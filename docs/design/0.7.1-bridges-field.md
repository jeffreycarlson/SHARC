# 0.7.1 — Container-driven `bridges` field on `SHARC:Renderer:render`

**Status:** Design (ready for implementation)
**Issue:** [#82](https://github.com/jeffreycarlson/SHARC/issues/82)
**Branch:** `feat/82-container-driven-bridges`
**Target version:** 0.7.1 (patch)
**Predecessors:** 0.7.0 GA (renderer protocol shipped). 0.7.2 (separate) will add OMID/OM SDK loading.

---

## 1. Problem statement

The renderer protocol shipped in 0.7.0 delivers `creativeHtml` to an operator-hosted renderer iframe, which writes it via `document.open()/write()/close()`. MRAID and SafeFrame creatives expect `window.mraid` and `window.$sf.ext` to exist *before* the first creative `<script>` runs — but the reference renderer at `examples/renderer/index.html` only installs the navigation bridge, never the MRAID/SafeFrame bridges. Today this works only because operators using the harness load creatives through `test/browser/{mraid,safeframe}-wrapper.html`, which manually imports the bridge modules. A renderer-protocol creative path has no such wrapper, so MRAID/SafeFrame APIs silently disappear and creatives break with no diagnostic. The creative validator surfaced this gap. We close it by having the container *tell the renderer* which bridges to load, via a new `bridges` field on the `SHARC:Renderer:render` message.

## 2. Wire-format change

A single new field on the `SHARC:Renderer:render` payload:

```typescript
{
  type: 'SHARC:Renderer:render',
  bridges: string[],              // NEW — see below
  containerOrigin: string,
  creativeHtml: string,
  placementSessionId: string,
  rendererProtocolVersion: '1',
  sharcNonce: string,
  sharcVersion: string,
}
```

**Position.** Alphabetical, immediately after `type`. Matches the existing field ordering convention in the protocol message.

**Type.** Flat `string[]` of lowercase bridge identifiers. Justification: the simplest serialization the protocol can carry. A `{ mraid: true, safeframe: false }` map adds nothing — the only state we model is "load this bridge or don't," and absence-from-array already means "don't." A flat array also reads identically to how operators reason about it ("this creative needs these bridges").

**Reserved bridge identifiers (0.7.1):**

| Identifier | Loads | Status |
|---|---|---|
| `'mraid'` | `sharc-mraid-bridge.mjs` | Implemented in 0.7.1 |
| `'safeframe'` | `sharc-safeframe-bridge.mjs` | Implemented in 0.7.1 |

**No reserved-future identifiers in 0.7.1.** Per the OMID-scope-split decision (§ 13 Q4), `'omid'` and any other future bridge identifiers are added to the protocol vocabulary at the release that implements them — not pre-reserved here. Unknown identifiers from a future-version container talking to a 0.7.1 renderer are tolerated by the validation rule below (forward-compat via silent skip), so pre-reservation buys nothing concrete and would publicly signal roadmap commitments we have not made.

**Empty-array semantics.** `bridges: []` = explicit "load no bridges" (e.g., a static-image creative the operator has explicitly classified). The renderer skips bridge loading entirely.

**Absent-field semantics.** A `:render` message without `bridges` (an old container talking to a new renderer, or vice versa) is treated identically to `bridges: []`. Old renderers ignore unknown fields and load no bridges — the same behavior as today, preserving backward compatibility. New renderers seeing absent `bridges` MUST NOT auto-detect from the markup; detection is a container responsibility (§ 3).

**Validation.** The renderer rejects `bridges` only if the field is present AND not an array of strings (`:failed` with `reason: 'invalid_bridges_field'`). Contents are not enforced — unknown identifiers are skipped with a `customSecurityLog` warning, not a fatal failure. Unknown-bridge tolerance is what makes the protocol forward-compatible: a future container that ships e.g. `bridges: ['mraid', 'sharc-1']` to a 0.7.1 renderer will load MRAID and skip the unknown identifier without breaking the render.

### 2.1 Runtime vs bridge — two concepts, two fields

The 0.7.1 design surfaces two related-but-distinct constructor options that are easy to conflate. Make the vocabulary explicit:

| Concept | Field | What it represents | Cardinality |
|---|---|---|---|
| API the creative declares | `creativeMeta.apis: number[]` | What the creative says it supports — AdCOM `APIFramework` integer codes | plural array |
| Bridge module the renderer loads | `bridges: string[]` | External compat layers loaded alongside the always-active runtime | plural array |
| Container's native runtime | (implicit, no accessor in 0.7.1) | The container IS SHARC 1.0 — always-active, never appears in `bridges` | singular identity |

**Key rule for 0.7.1: the AdCOM code for SHARC 1.0 (TBD per upstream contribution; see § 6.1) does NOT map to any bridge identifier.** SHARC 1.0 IS the runtime; nothing to load externally for it. A creative declaring SHARC support runs natively without any bridge load.

The `bridges` allowlist for 0.7.1 is `'mraid'` and `'safeframe'` (latter via adm scan today; via `creativeMeta.apis` once AdCOM adds the SafeFrame enum). 0.7.2 will add `'omid'` for OMID viewability (separate scope per § 13 Q4); future SHARC 2.0+ extends the allowlist further with `'sharc-1'` etc. (see § 11.1 *Per-major-version bridges allowlist expansion*).

## 3. Container-side detection

Three-layer pipeline. The result is the array sent in `bridges`. Order is precedence: explicit beats `creativeMeta.apis` beats adm scan.

### 3.1 Layer 1 — Explicit constructor option

Operators provide an explicit override via the new constructor option `bridges` (same name as the protocol field — keeps the mental model thin).

| Value | Meaning |
|---|---|
| `undefined` (omit) | Auto-detect (fall through to layer 2) |
| `null` | Auto-detect (explicit "use auto-detection"; identical to `undefined`) |
| `[]` | Empty array — load no bridges, even if the markup looks like it needs them |
| `['mraid']`, `['safeframe']`, `['mraid', 'safeframe']` | Load exactly the named bridges |

**Type:** `string[] | null`. A boolean toggle map (`{ mraid: true, safeframe: false }`) is rejected — operators thinking in those terms can pass `['mraid']` instead, and the API is one shape for both wire and constructor.

**Validation.** If `bridges` is provided and is not `null` or an array of strings, the constructor throws `TypeError`. Contents are validated against the reserved identifiers (`'mraid'`, `'safeframe'`); unknown identifiers throw `Error` listing the accepted values. This is stricter than the renderer-side handling because operator constructor input is authored by humans and a typo deserves a loud failure.

### 3.2 Layer 2 — `creativeMeta.apis` flag pass-through

`creativeMeta.apis` carries the **AdCOM `APIFramework` integer codes** the bid response declared (MRAID 1/2/3 = `3/5/6`, OMID = `7`, etc. per [AdCOM v1.0 List: API Frameworks](https://github.com/InteractiveAdvertisingBureau/AdCOM/blob/master/AdCOM%20v1.0%20FINAL.md#list--api-frameworks-)). AdCOM is the source of truth — SHARC's contract is anchored to AdCOM, not to any specific OpenRTB version. When present, this is the most reliable signal because it represents an upstream judgment about the creative.

For OpenRTB 2.6 users the mapping is direct (OpenRTB 2.6's `bid.apis` references AdCOM enums). For pre-2.6 sources where the field is the deprecated singular `bid.api` (single integer), operators normalize at their call site before passing to SHARC:

```ts
creativeMeta: { apis: bid.apis ?? (typeof bid.api === 'number' ? [bid.api] : bid.api ?? []) }
```

**The container does not currently accept bid metadata.** This design adds a new constructor option:

```typescript
creativeMeta?: {
  apis?: number[];   // AdCOM APIFramework integer codes
}
```

`creativeMeta` is the container's general slot for bid-side metadata. We keep the AdCOM shape (a `number[]` of API framework codes) rather than translating to bridge names at the call site — operators forwarding bid data should pass it through verbatim, and the container does the translation:

| AdCOM `APIFramework` code | Bridge identifier |
|---|---|
| `3` (MRAID 1.0) | `'mraid'` |
| `5` (MRAID 2.0) | `'mraid'` |
| `6` (MRAID 3.0) | `'mraid'` |
| `7` (OMID 1.0) | (reserved — 0.7.2) |
| _SafeFrame (TBD AdCOM code, not yet assigned)_ | `'safeframe'` (post-AdCOM addition) |
| _SHARC (TBD AdCOM code, not yet assigned)_ | (none — runtime is always-active, no bridge to load) |
| Other / vendor-specific (`500+`) | Ignored |

Codes for SafeFrame and SHARC do not exist in AdCOM today; they are SHARC's planned upstream contributions (see § 6.1 *Future AdCOM enum additions*). Specific code numbers are TBD per AdCOM PR review (assigned at next-available-code positions at time of merge — pre-committing to specific integers risks collision with concurrent additions like a future SIMID 1.2). Until those land, SafeFrame detection falls through to the layer-3 adm scan; SHARC-native creatives need no detection because the runtime is always active.

**Why a new option, not an extension of `environmentData`.** `environmentData` is creative-facing context (volume, page URL, sfMeta). Bridge detection is operator-facing wiring config. Conflating them would be confusing and would push API-framework metadata into the `Container:init` payload where it does not belong.

**Layer-2 fall-through.** If `creativeMeta.apis` is present and non-empty, layer 2 produces the bridge list. Otherwise (absent, empty, or contains only unrecognized codes), fall through to layer 3.

### 3.3 Layer 3 — Adm content scan

Last-resort heuristic. Scans `creativeHtml` for tighter substrings than the issue's loose `indexOf('mraid')`:

| Bridge | Match condition (any one is sufficient) |
|---|---|
| `'mraid'` | `creativeHtml.indexOf('mraid.js') !== -1` |
| `'safeframe'` | `creativeHtml.indexOf('$sf.ext') !== -1` |

Both patterns are case-sensitive. Rationale:

- `mraid.js` is the canonical script name MRAID creatives reference and is far more specific than the bare token `mraid` (which collides with comments, CSS class names, analytics tags). False negatives (a creative that calls `mraid.foo()` without ever loading `mraid.js`) are tolerable per the OpenClaw call — operators can pass the explicit `bridges` option.
- `$sf.ext` is the SafeFrame creative API entry point. Any SafeFrame creative that does anything beyond a static render calls into `$sf.ext` directly, and the literal token is uncommon in non-SafeFrame markup.

**Why SafeFrame is adm-scan-only in 0.7.1.** SafeFrame creatives are detected via adm content scan rather than a `creativeMeta.apis` signal because no AdCOM `APIFramework` enum value exists for SafeFrame. The SafeFrame 2.0 working group's effort to define a bid-time declaration mechanism ([SafeFrame 2.0 draft, July 2020](https://iabtechlab.com/wp-content/uploads/2020/07/IAB-Tech-Lab-SafeFrame-2-0-draft-for-public-comment-2020-07-29.pdf), pp. 10–11 *Header Bidding* — never finalized) transformed into the SHARC initiative, which subsumes both SafeFrame and MRAID. SHARC's planned upstream contribution to IAB Tech Lab proposes adding both SafeFrame 1.0 and SHARC 1.0 to AdCOM's `APIFramework` enum, closing the 13-year-old gap and registering the unified successor in one move (see § 6.1 *Future AdCOM enum additions*). Until those AdCOM additions land, adm content scan (`indexOf('$sf.ext')`) is the bridge for legacy SafeFrame creatives.

**Cost.** Two `String.prototype.indexOf` calls on a 256 KiB-max payload. V8 indexOf on a 256 KB string is sub-millisecond on commodity hardware. Tested explicitly in the perf test (§ 7).

**Failure mode.** If neither pattern matches, the layer returns `[]` and the renderer loads no bridges. False negatives are loud (creative breaks) but easily fixed (operator passes explicit `bridges`).

### 3.4 Resolution algorithm (pseudocode)

```
function resolveBridges(opts) {
  // Layer 1 — explicit
  if (Array.isArray(opts.bridges)) return [...opts.bridges].sort();
  // (null and undefined fall through)

  // Layer 2 — creativeMeta.apis (AdCOM APIFramework codes)
  if (opts.creativeMeta && Array.isArray(opts.creativeMeta.apis) && opts.creativeMeta.apis.length) {
    const fromBidApis = mapAdComApisToBridges(opts.creativeMeta.apis);
    if (fromBidApis.length) return fromBidApis.sort();
  }

  // Layer 3 — adm content scan (Markup variant only — Creative URL has no adm)
  if (opts.creativeHtml) {
    const fromScan = scanAdm(opts.creativeHtml);
    if (fromScan.length) return fromScan.sort();
  }

  return [];
}
```

The layers are evaluated in strict order; the first one that yields a non-empty result wins. Empty layer-1 (`bridges: []`) terminates the pipeline at "no bridges" — that is the explicit override.

The result array is **sorted** before placement on the `:render` message. Stable ordering matters for replay-safe logs and for tests that snapshot the message payload.

The internal helper that runs this pipeline is `_resolveBridges()` on `SHARCContainer`.

### 3.5 Multi-framework declaration truth table

`creativeMeta.apis` is a plural array — creatives commonly declare multiple frameworks (e.g. MRAID + OMID, or SHARC-native with MRAID-3 fallback). The default rule: **load every bridge whose AdCOM code maps to a known bridge identifier; deduplicate; sort.** Operators override via the explicit `bridges: [...]` constructor option (layer 1).

In the table below, real AdCOM codes are integers (`3`, `5`, `6`, `7`); placeholder labels (`<SHARC1>`, `<SHARC2>`, `<SF>`) stand in for AdCOM codes that have not yet been assigned (see § 6.1 — code numbers are TBD per AdCOM PR review):

| `creativeMeta.apis` | Resolved `bridges` (SHARC 1.0 / 0.7.1) | Notes |
|---|---|---|
| `[]` or absent | `[]` (or layer-3 adm scan result) | No bid-time signal; falls through to adm scan |
| `[3]`, `[5]`, `[6]` | `['mraid']` | Pure MRAID at any version |
| `[3, 5, 6]` | `['mraid']` | All MRAID versions declared (deduplicated to single bridge) |
| `[7]` | `[]` (0.7.1) / `['omid']` (0.7.2) | Pure OMID — deferred per scope split |
| `[6, 7]` | `['mraid']` (0.7.1) / `['mraid', 'omid']` (0.7.2) | MRAID + OMID, common combo |
| `[<SHARC1>]` | `[]` | Pure SHARC-native creative — runtime always active, no bridge needed |
| `[6, <SHARC1>]` | `['mraid']` | Forward/backward compat — creative supports SHARC OR MRAID 3.0; container loads MRAID bridge defensively (creative may still call `mraid.*`) |
| `[<SHARC2>]` | `[]` | Future SHARC 2.0 declared; current 1.0 container has no compat layer — silent (creative may break if it calls 2.0-only APIs) |
| `[<SHARC2>, <SHARC1>]` | `[]` | Forward-compat declaration; 1.0 container ignores future code, sees native SHARC 1.0 |
| `[<SHARC2>, 6]` | `['mraid']` | Future SHARC 2.0 OR MRAID 3.0; current container falls back to MRAID |
| `[<SF>]` (post-AdCOM) | `['safeframe']` | Pure SafeFrame legacy (after AdCOM enum lands; pre-AdCOM: adm scan) |
| `[<SF>, <SHARC1>]` (post-AdCOM) | `['safeframe']` | SafeFrame legacy + SHARC migration target |
| `[500+]` (vendor-specific) | `[]` | AdCOM vendor-specific codes; SHARC ignores in detection. Explicit `bridges: [...]` is the override path |

**Why load defensively when SHARC + MRAID both declared.** The creative might still call `mraid.*` even when `SHARC.*` is available — author habit, mixed code paths, third-party measurement scripts compiled against MRAID. Loading the MRAID bridge is cheap (~3–5 KB) and harmless (defines `window.mraid`; unused identifiers don't hurt). Skipping creates the silent-break failure mode 0.7.1 is supposed to prevent.

**Unrecognized codes (vendor-specific, future enum, typo).** Layer 2 ignores them and falls through. They never produce a "load nothing on purpose" signal — that's what an explicit `bridges: []` is for. Operators who need to suppress detection for a specific creative pass `bridges: []` at the call site.

## 4. Renderer-side bridge loading

### 4.1 Where in the render flow

Bridge loading slots in between **navigation bridge install** (existing) and **`document.write(html)`** (existing). Per `examples/renderer/index.html` line 689–727, the navigation bridge install is the last step before the meta-refresh strip and the `onBeforeRender` hook. Bridges from the new field go in *immediately after* the navigation bridge install, *before* the meta-refresh strip:

```
acceptAndRender(data)
├─ beforeStorageClear hook
├─ history.replaceState (clear nonce)
├─ install navigation bridge          (existing)
├─ load bridges from data.bridges     (new — § 4.2)
├─ stripMetaRefresh
├─ onBeforeRender hook
├─ DOMContentLoaded listener
├─ document.open / write / close
└─ onAfterRender hook → :rendered
```

Order rationale: the navigation bridge installs capture-phase event listeners on `window`/`document` whose identity persists across `document.open()`. Once it's installed, any further bridge that touches the same DOM is well-defined. The MRAID/SafeFrame bridges install `window.mraid` / `window.$sf.ext` — neither needs to come before navigation, but both MUST come before `document.write` so the creative's first synchronous script sees the API.

### 4.2 How the renderer fetches bridge code

**Convention: renderer-relative path.** The renderer at `<origin>/<path>/renderer/index.html` fetches each bridge from `<origin>/dist/sharc-<bridge>-bridge.mjs`. Concrete shape for each reserved identifier:

| `bridges` entry | Fetched URL (relative to renderer page) |
|---|---|
| `'mraid'` | `../../dist/sharc-mraid-bridge.mjs` |
| `'safeframe'` | `../../dist/sharc-safeframe-bridge.mjs` |

This matches the existing navigation-bridge wiring (line 198: `from '../../dist/sharc-navigation-bridge.mjs'`) so the hosted reference at `jeffreycarlson.github.io/SHARC/dist/sharc-mraid-bridge.mjs` already resolves without any operator action.

**Operator override.** A new `RENDERER_CONFIG.BRIDGE_URL_TEMPLATE` value (default: `'../../dist/sharc-{name}-bridge.mjs'`) lets operators forking the renderer point at a different layout. The `{name}` token is replaced with the bridge identifier. Forks that bundle differently override this; defaults Just Work for the canonical fork-and-deploy path.

The decision to make the URL **convention-based, not container-supplied** is deliberate. Letting the container dictate URLs would let a compromised publisher script point the renderer at attacker-controlled bridge code — collapsing the cross-origin sandbox guarantee. Bridge code lives next to the renderer, on the renderer's origin, full stop.

### 4.3 Loading mechanism

Each bridge is loaded via dynamic `import()`. The renderer awaits all imports in parallel before proceeding to `document.write`:

```javascript
const bridgesToLoad = Array.isArray(data.bridges) ? data.bridges : [];
const knownBridges = ['mraid', 'safeframe'];
const installPromises = bridgesToLoad
  .filter(b => knownBridges.indexOf(b) !== -1)
  .map(b => loadBridge(b));  // loadBridge does import + install
await Promise.all(installPromises);
```

`loadBridge(name)` resolves the URL via `BRIDGE_URL_TEMPLATE`, calls `import(url)`, and the bridge module's auto-install fires on evaluation (§ 5). The `await Promise.all(...)` guarantees all bridges are installed before `document.write`.

### 4.4 Failure modes

| Condition | Behavior |
|---|---|
| Unknown identifier in `bridges` | Skipped silently; `customSecurityLog` warns with `reason: 'unknown_bridge_skipped'` and the identifier name. Render proceeds. |
| `data.bridges` present but not an array of strings | `:failed` with `reason: 'invalid_bridges_field'` |
| `import()` rejects (404, MIME mismatch, network) | `:failed` with `reason: 'bridge_load_failed'` and the identifier in the failure log; container surfaces it as `RENDERER_FAILED (2115)` |
| Bridge module throws on evaluation | `:failed` with `reason: 'bridge_install_threw'` |

**Why fail-loud on bridge load.** The whole point of the field is that bridge absence today is silent. If the container said "load MRAID" and the renderer can't, that's a deployment defect the operator MUST see at the next render. Falling through to "render without the bridge and let the creative break" reproduces the bug we're fixing.

The 2s `:rendered` reply timeout includes bridge-load time. On commodity networks, two `import()` calls on a same-origin renderer should complete in <100 ms. The ALCS budget is comfortable. If operators see timeouts on bridge load, that's a surfaced infra problem — preferable to silent break.

## 5. Bridge module changes (`src/sharc-{mraid,safeframe}-bridge.js`)

Today's bridges (lines 957–969 of `sharc-mraid-bridge.js`, lines 641–652 of `sharc-safeframe-bridge.js`) install only when loaded as a `<script>` tag *and* `window.SHARC.onReady` is already defined — i.e., when SHARC SDK is already on `window`. Inside the renderer protocol flow, the SHARC SDK lives inside `creativeHtml` and is not on `window` at module-evaluation time. The current install path will not fire.

**Required change: opt-in renderer-side auto-install, mirroring the navigation bridge.** Each bridge gets a guarded auto-install that fires when the host explicitly opts in via a flag set on `window` *before* the module loads.

For the MRAID bridge:

```javascript
// At the bottom of sharc-mraid-bridge.js, ALONGSIDE the existing
// SDK-loaded auto-install. Renderer-side path:
if (typeof window !== 'undefined') {
  /** @type {any} */
  var anyWin = window;
  if (anyWin.__sharcMraidBridgeAutoInstall && !anyWin.__sharcMraidBridgeInstalled) {
    installMRAIDBridge(window.SHARC || {});
    anyWin.__sharcMraidBridgeInstalled = true;
  }
}
```

`installMRAIDBridge(SHARC)` is then called with whatever shape `window.SHARC` has at module-evaluation time. If `SHARC` is empty, the install needs to be safe (the bridge picks up `window.SHARC.onReady` lazily when the SDK loads inside the creative document — same lazy-lookup pattern the navigation bridge uses for `requestNavigation`).

The renderer sets `window.__sharcMraidBridgeAutoInstall = true` *before* the dynamic `import()`. Same pattern as the existing `__sharcNavBridgeAutoInstall`. SafeFrame gets the symmetric `__sharcSafeFrameBridgeAutoInstall` / `__sharcSafeFrameBridgeInstalled` pair.

**Side-by-side load-paths preserved.** The existing wrapper-driven install path (where the wrapper page sets up `window.SHARC` first and then loads the bridge as a classic `<script>`) keeps working unchanged. The new flag-gated path is additive. Test/browser harness pages do NOT need to change in 0.7.1 (§ 7).

**Idempotency.** The `__sharcMraidBridgeInstalled` / `__sharcSafeFrameBridgeInstalled` flags guard against double-install if the renderer's `import()` resolves twice (it shouldn't, but module caching across a `:render` retry is hypothetically possible). Same shape as `__sharcNavBridgeInstalled`.

## 6. Constructor option design

```typescript
new SHARCContainer({
  // existing options...
  bridges?: string[] | null,
  creativeMeta?: { apis?: number[] },
})
```

| Option | Type | Default | Semantics |
|---|---|---|---|
| `bridges` | `string[] \| null` | `undefined` (auto-detect) | Explicit override. `null` is identical to omit. `[]` = "load no bridges." `['mraid', 'safeframe']` = load both. |
| `creativeMeta` | `{ apis?: number[] }` | `undefined` | Bid-side metadata. `creativeMeta.apis` is the AdCOM `APIFramework` integer code list, mapped to bridge identifiers per § 3.2. Future fields may live here. |

**AdCOM as source of truth.** `creativeMeta.apis` values are [AdCOM v1.0 `APIFramework`](https://github.com/InteractiveAdvertisingBureau/AdCOM/blob/master/AdCOM%20v1.0%20FINAL.md#list--api-frameworks-) integer codes — NOT OpenRTB version-specific values. AdCOM is the registry; OpenRTB consumes it. Anchoring SHARC's contract to AdCOM keeps the field stable across OpenRTB version churn. For OpenRTB 2.6 users, `bid.apis` maps directly (it references AdCOM enums). For pre-2.6 sources where the field is the deprecated singular `bid.api`, operators normalize at their call site:

```ts
creativeMeta: { apis: bid.apis ?? (typeof bid.api === 'number' ? [bid.api] : bid.api ?? []) }
```

Pre-existing AdCOM codes used in 0.7.1 detection: `3` (MRAID 1.0), `5` (MRAID 2.0), `6` (MRAID 3.0).

Both options live in the existing constructor `options` destructure (around line 410–440) and are validated alongside the other sequenced rules in `_validateOptions`/the constructor body. The `bridges` validator runs in the same group as Rules 1–8 (Creative Sources), preceded by adding a new "Rule 9: `bridges` is null/undefined or a string array of recognized identifiers."

`creativeMeta` does not need a sequenced rule — it's metadata, not a constraint check. Validation: if present, `creativeMeta` must be an object (TypeError), and `creativeMeta.apis` if present must be an array of numbers (TypeError). Unrecognized codes are silently ignored (per § 3.2).

The constructor option list in JSDoc gets two new entries, alphabetically inserted (between `creativeMeta` after `autoStart` if alphabetical, or grouped with creative-sources options — match the existing pattern).

The container exposes the resolved bridges list for diagnostics: `container.bridges` (frozen array, lazy on first read or eagerly populated post-construction). Useful for operator dashboards correlating "this `placementSessionId` had MRAID bridge loaded" without re-running the detection. **No `container.runtimeApi` accessor in 0.7.1** — at SHARC 1.0 it would be a constant for the entire 1.0 lifetime (0.7.x → 0.8.x → 0.9.x). Deferred until SHARC 2.0+ ships, when a second runtime version makes the accessor a meaningful diagnostic surface (see § 11.2 *Future `container.runtimeApi` accessor*).

### 6.1 Future AdCOM enum additions (upstream contribution roadmap)

SHARC's planned upstream contribution to IAB Tech Lab will file an AdCOM PR proposing **two new `APIFramework` enum values, registered together**:

- **SafeFrame 1.0** — closes a 13-year gap. SafeFrame predates AdCOM's `APIFramework` enum and was never assigned a code. The SafeFrame 2.0 working group's planned bid-time declaration mechanism (per the [SafeFrame 2.0 draft, July 2020](https://iabtechlab.com/wp-content/uploads/2020/07/IAB-Tech-Lab-SafeFrame-2-0-draft-for-public-comment-2020-07-29.pdf), pp. 10–11) never finalized — that effort transformed into SHARC. SHARC's contribution closes the legacy gap as part of its own registration.
- **SHARC 1.0** — registers SHARC's identity as a creative-runtime API at the same conceptual level as MRAID and OMID.

Both enum values **MUST be filed together**. The dual-registration framing positions SHARC's contribution as completing IAB-stack work — closing a long-standing gap *and* registering the unified successor — rather than as a self-promotional single enum-add for the new framework.

**Specific code numbers are TBD per AdCOM PR review** — both values are assigned at next-available-code positions at time of merge. We deliberately avoid pre-committing to specific integers (e.g. "code 10 = SafeFrame, code 11 = SHARC") because concurrent additions could claim those slots first — a future SIMID 1.2, OMID 2.0, or any other in-flight enum proposal could land at the next-available code before SHARC's PR. Pre-committing to specific numbers in operator-facing docs would force a documentation-update scramble. This design doc and the implementation use placeholder labels (`<SHARC1>`, `<SF>`, etc.) until AdCOM merge assigns the real values.

This is **forward-looking only**. The AdCOM PR and the WG conversation are separate operator-decision items requiring explicit go-ahead; nothing about this design pass files them. The 0.7.1 implementation works with the AdCOM enum as it stands today, and gracefully picks up the SafeFrame and SHARC codes when (if) they land.

## 7. Test strategy

### 7.1 New: `test/node/test-bridges-detection.js`

Pure unit tests on the `_resolveBridges()` algorithm. jsdom-based, no Puppeteer.

Coverage matrix:

- **Layer 1 (explicit):** `null`, `[]`, `['mraid']`, `['safeframe']`, `['mraid', 'safeframe']`, invalid types (`true`, `'mraid'`, `42`), unknown identifiers (`['omid']` — deferred to 0.7.2 in the constructor as an unknown identifier; throws).
- **Layer 2 (`creativeMeta.apis`):** absent, empty, codes `3/5/6` → `['mraid']`, post-AdCOM `10` → `['safeframe']`, `[5, 10]` → `['mraid', 'safeframe']`, `[11]` → `[]` (SHARC native, no bridge), `[6, 11]` → `['mraid']` (defensive load), unrecognized codes (`100`, vendor-specific `500+`) → ignored. Truth-table coverage per § 3.5.
- **Layer 3 (adm scan):** matches on `mraid.js`, `$sf.ext`; non-matches on bare token `mraid`, `safeframe` (without the `$sf.ext` accessor); empty `creativeHtml` (Creative URL variant — layer 3 short-circuits).
- **Precedence:** explicit `[]` short-circuits even when creativeMeta + adm would both detect. `creativeMeta.apis: [5]` overrides adm content with `mraid.js` if both present (layer 2 wins). Adm scan only fires when both higher layers are empty.
- **Sort stability:** input `['safeframe', 'mraid']` produces output `['mraid', 'safeframe']` regardless of insertion order.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Bridge load failure mid-render — what does the operator see? | `:failed` with `reason: 'bridge_load_failed'`, surfaced as `RENDERER_FAILED (2115)`. The container's existing `onSecurityEvent` carries the reason raw. Operators get a structured signal. |
| Renderer version mismatch — operator hasn't upgraded their fork | Backward-compatible. Old renderer ignores `bridges`, loads no bridges, creative breaks at MRAID API access — same failure mode as today. No regression. |
| Adm scan false negative (bridge not loaded when needed) | Acceptable per the OpenClaw call. Explicit `bridges` constructor option is the override. Documented in the cookbook. |
| Adm scan false positive (extra bridge loads needlessly) | Acceptable — bridge install is idempotent and the cost is one `import()` (<100 ms cached). Strictly preferable to a false negative. |
| Detection cost on large `creativeHtml` | Two `indexOf` calls on 256 KiB ≈ sub-millisecond on V8. Asserted by the perf test. |
| Constructor option proliferation | `creativeMeta` is a forward-compatible bag (`apis?: number[]`). Future bid-side fields land in the same object without growing the constructor surface. |
| Operator forks bundling differently | `RENDERER_CONFIG.BRIDGE_URL_TEMPLATE` is the override. Convention-by-default keeps the canonical fork zero-config. |
| `creativeHtml` 256 KiB cap interaction | Unchanged. The cap applies pre-injection; `bridges` does not modify `creativeHtml`. |
| Container-side detection diverging from renderer-side capability | The renderer holds the truth: it filters `bridges` against its `knownBridges` allowlist (`['mraid', 'safeframe']` in 0.7.1). A container that ships `'omid'` to a 0.7.1 renderer gets a `customSecurityLog` skip, not a render failure. |

## 11. Forward-looking notes

Items NOT in 0.7.1 scope, recorded here so the design's evolution path stays coherent. None of these are blockers; all are deferred until the right moment.

### 11.1 Per-major-version bridges allowlist expansion

Each new SHARC major version ships its predecessor as a compat bridge. AdCOM `APIFramework` enum codes are stable across SHARC versions; bridge identifiers expand:

| SHARC version | `bridges` allowlist |
|---|---|
| **1.0** (this PR's target — 0.7.1) | `'mraid'`, `'safeframe'` (latter via adm scan today; via `creativeMeta.apis` once AdCOM adds the SafeFrame enum) |
| **1.0** (0.7.2 follow-up) | above + `'omid'` (OMID viewability — separate scope per § 13 Q4) |
| **2.0** (future major) | above + `'sharc-1'` (loads `sharc-1-compat.mjs` translating SHARC 1.0 API calls into 2.0 internals) |
| **3.0** (further future) | above + `'sharc-2'` |

The MRAID precedent: `'mraid'` is one bridge module that internally handles AdCOM codes `3/5/6` because MRAID's evolution was additive within a single API surface. SHARC's evolution may be cleaner-break per-major version (per the SafeFrame 2.0 → SHARC heritage, where the successor was a re-architecture rather than an additive revision), so each compat layer is its own bridge module addressed by its own identifier.

### 11.2 Future `container.runtimeApi` accessor (NOT in 0.7.1)

When SHARC 2.0+ introduces a second runtime version, a `container.runtimeApi` accessor (frozen string, e.g. `'sharc-1.0'` or `'sharc-2.0'`) becomes a meaningful operator-facing diagnostic — it lets dashboards and observability pipelines distinguish "this placement ran on a 1.x container" from "this placement ran on a 2.x container."

At SHARC 1.0 the accessor would be a constant for the entire 1.0 lifetime (`0.7.x → 0.8.x → 0.9.x → 1.0`). Adding it now is YAGNI surface area for zero diagnostic value. Operators who need implementation-version info today read `SHARC_VERSION` exported from `sharc-protocol.js`. Once SHARC 2.0 ships, the `container.runtimeApi` accessor plus its corresponding AdCOM `APIFramework` code form a coherent diagnostic surface — added then, not now.

### 11.3 Dual AdCOM enum-registration upstream contribution

Cross-reference: § 6.1 *Future AdCOM enum additions*. SafeFrame 1.0 + SHARC 1.0 enum codes are filed together as a single AdCOM PR. Forward-looking only — not part of this design pass.

## 13. Design decisions (resolved)

All seven design questions are resolved. The Senior Developer implements against these locks; the conversation that produced them is summarized in § 14.

1. **Constructor option name + type.** **Resolved (Jeffrey, 2026-05-09):** ship `bridges: string[] | null` (mirrors the protocol field) and `creativeMeta: { apis?: number[] }` (forward-compatible bag; `apis` plural mirrors OpenRTB 2.6's modern `bid.apis` and disambiguates from the deprecated singular `bid.api`). PM concurred with architect.

2. **Bridge URL discovery.** **Resolved (Jeffrey, 2026-05-09):** convention-based (`<renderer-origin>/dist/sharc-{name}-bridge.mjs`), overridable via `RENDERER_CONFIG.BRIDGE_URL_TEMPLATE`. Container does NOT specify URLs (security boundary). Security Engineer added 5 required guardrails baked into § 4.

3. **Harness migration.** **Resolved (Jeffrey, 2026-05-09):** `test/browser/{mraid,safeframe}-test.html` stay on the wrapper pattern in 0.7.1. Spec'd mechanism is renderer-domain; migration is a separate follow-up.

4. **OMID slot reservation.** **Resolved (Jeffrey, 2026-05-09): keep `'omid'` out of 0.7.1 entirely.** The protocol vocabulary, renderer allowlist, and operator-facing docs all omit `'omid'` until 0.7.2 ships it. Wire-format collision risk is theoretical; PM's no-speculative-version-tagging principle (memory `feedback_avoid_speculative_version_tagging`) wins. A future 0.7.2 container talking to a 0.7.1 renderer will have its `'omid'` identifier silently skipped per the validation rule in § 2 (forward-compat via tolerance, not pre-reservation).

5. **Validator integration.** **Resolved (Jeffrey, 2026-05-09):** separate follow-up on the spike branch (`spike/sharc-creative-validator`). NOT folded into the 0.7.1 PR. Once 0.7.1 ships, the spike updates to drop manual bridge loading and adopt the spec mechanism.

6. **`container.bridges` diagnostic accessor.** **Resolved (Jeffrey, 2026-05-09):** ship as frozen array, set during construction. PM noted this is the affordance that makes 0.7.1 actually solve the "why isn't MRAID working" support ticket. NO `container.runtimeApi` accessor in 0.7.1 (deferred to SHARC 2.0+ — see § 11.2).

7. **Async `acceptAndRender`.** **Acknowledged (Jeffrey, 2026-05-09):** renderer function becomes async to await `import()`. The existing 2s `:rendered` reply timeout absorbs the latency. Operator hook contract (`onBeforeRender`, `onAfterRender`, etc.) stays synchronous-required.

## 14. Design discussion summary

This design doc was produced over a multi-turn conversation (2026-05-09) between Jeffrey, the Software Architect, and two specialist subagents (Product Manager, Security Engineer). The load-bearing decision moves, in order:

### Subagent involvement
Per Jeffrey's directive ("make sure subagents are involved in the design"), the Software Architect produced an initial design doc, then Product Manager + Security Engineer reviewed in parallel for operator-facing surface decisions and security-load-bearing decisions respectively. Each subagent surfaced findings the others missed: PM contradicted the architect on Q4 (OMID slot), SE added 5 required guardrails to Q2 (bridge URL discovery), Architect's spec-fidelity baseline tied them together.

### AdCOM as the spec anchor (not OpenRTB)
Jeffrey's instinct early in the conversation: "Should SHARC have its own API that things map to?" Followed by the sharper insight: "SHARC should just map to AdCOM like the OpenRTB spec does?" This shifted `creativeMeta`'s semantic anchor from "OpenRTB-aligned" to "AdCOM-aligned" — a decoupling from OpenRTB version churn that positions SHARC correctly within the IAB spec stack. AdCOM v1.0 (March 2022) became the canonical reference for `creativeMeta.apis` values.

### SafeFrame 2.0 → SHARC heritage
Investigation of why SafeFrame is missing from AdCOM's `APIFramework` enum surfaced that the SafeFrame 2.0 effort (2020 draft for public comment, never finalized) **transformed into SHARC** rather than stalling. The IAB Tech Lab energy moved from "finalize SafeFrame 2.0 + add to AdCOM" to "build SHARC as the unified successor to SafeFrame and MRAID." This reframes SHARC's contribution to IAB Tech Lab as completing work the SafeFrame 2.0 working group started.

### Dual AdCOM enum registration roadmap
Jeffrey: "It might be worthwhile for SafeFrame 1 to still have an enum with the release of SHARC." This produced the dual-registration plan: when SHARC contributes upstream to IABTechLab, the AdCOM PR proposes adding **both** SafeFrame 1.0 and SHARC 1.0 to `APIFramework` together. Closes a 13-year gap (SafeFrame's missing enum) AND registers the unified successor in one move. Stewardship framing, not self-promotion.

### Placeholder labels instead of speculative integer codes
Initial design pre-committed to "code 10 = SafeFrame, code 11 = SHARC." Jeffrey: "Would prefer A but that could change if SIMID 1.2 came out first." The conservative move: placeholder labels (`<SHARC1>`, `<SF>`, etc.) throughout the doc instead of integer codes that AdCOM may assign differently. The single deliberate exception is § 6.1's caveat paragraph that uses "10/11" as the example of what to avoid pre-committing to.

### Runtime-vs-bridge vocabulary distinction
Jeffrey's contribution: "In SHARC, 11 is always available but perhaps 12 is SHARC 2 and the 2.0 Container has a compatibility bridge for 11." This crystallized the distinction between `creativeMeta.apis` (creative declarations) vs. `bridges` (loaded compat modules) vs. the implicit always-active runtime. § 2.1 captures this as a three-row vocabulary table.

### `container.runtimeApi` accessor — YAGNI walk-back
Initial design proposed `container.runtimeApi: 'sharc-1.0'` alongside `container.bridges`. Jeffrey: "But if the runtime is always SHARC 1.0, why add this now?" Right call — the accessor would be a constant for the entire 1.0 lifetime (0.7.x → 0.8.x → 0.9.x), zero diagnostic value at SHARC 1.0. Deferred to SHARC 2.0+ when a second runtime version makes the accessor a meaningful diagnostic surface.

### OpenRTB 2.6 `apis` rename
Jeffrey's spec-knowledge catch: "We may also want to declare apis instead of api consistent with OpenRTB 2.6." Verified: OpenRTB 2.6 deprecated singular `bid.api` (was a single integer) in favor of plural `bid.apis` (integer array). Renamed `creativeMeta.api` → `creativeMeta.apis` throughout the design.

### OMID-out-of-0.7.1 lock (resolves PM/Architect disagreement)
The architect recommended pre-reserving `'omid'` in 0.7.1's protocol vocabulary; PM contradicted, citing memory `feedback_avoid_speculative_version_tagging`. Jeffrey sided with PM: "keep omid out until 0.7.2." Wire-format collision risk is theoretical; the `bridges` field validation rule in § 2 already tolerates unknown identifiers from future-version containers (forward-compat via silent skip), so pre-reservation buys nothing concrete and would publicly signal an unmade commitment.

### Conservative defaults applied throughout
Cookbook cell density: leave dense (operator reference material belongs near the field). Async `acceptAndRender`: implementation detail, no operator-visible contract change. Harness migration: out of 0.7.1 scope. SafeFrame detection: adm-scan-only until AdCOM enum lands, no pre-committed bridge code. Each conservative call follows the same principle — ship only what 0.7.1 actually delivers; defer everything that requires speculation about future spec evolution or operator behavior.
