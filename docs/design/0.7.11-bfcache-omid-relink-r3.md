## 1. Context — what #338 actually is (two independent failures under one ticket)

The lifecycle audit filed NEW-C (P1) from finding **F6**: after a bfcache round-trip, OMID can remain `NON_VISIBLE` even though the ad is back on screen. The ticket and the audit name two root causes. Grounding both in code at `origin/main` (worktree built from `ad5038c`, the R1/contract landing):

### 1.1 Failure A — OMID stuck `NON_VISIBLE` (container-side, port-INDEPENDENT)

This is the headline symptom and it does **not** involve the MessagePort at all. The OMID bridge is a **publisher-page / container-side extension** (`sharc-omid-bridge.js:6` — "the 0.7.3 path is container-owned: the publisher page loads … owns AdSession lifecycle"). Its visibility signal `adEvents.stateChange('VISIBLE'|'NON_VISIBLE')` is called **directly against the OM SDK AdSession on the publisher page** (`sharc-omid-bridge.js:1161-1163`) — it never traverses the creative MessagePort. So whether the port is alive or dead is irrelevant to Failure A. Failure A is a pure **edge-trigger + driver-race** bug:

**Fact A1 — OMID visibility is driven only by a real state-machine transition.** `onContainerStateChange` (`sharc-omid-bridge.js:692-712`) calls `_signalVisibility('visible')` on `active` (`:702`) and `_signalVisibility('notVisible')` on `passive`/`hidden`/`frozen` (`:706`). `onContainerStateChange` is invoked only from `_notifyExtensionsLifecycle('stateChange', …)` (`sharc-container.js:1890-1891`), which fires **only** inside the state machine's `onChange` callback (`sharc-container.js:1539-1543`). `onChange` fires only on an **actual** state transition. **A no-op `setState(ACTIVE)` — calling `setState(ACTIVE)` when the container is already ACTIVE — produces no `onChange`, no extension notify, no `_signalVisibility('visible')`.** (This is the same already-ACTIVE-skip class as #336, but here it bites OMID on the *restore* path.)

**Fact A2 — `_signalVisibility` is itself edge-/level-guarded on `lastVisibilityState`.** `_signalVisibility` early-returns when `this._omid.lastVisibilityState === visibilityState` (`sharc-omid-bridge.js:1158`). This guard is correct (it is the OMID-side dedup). But combined with Fact A1 it means: the **only** way OMID flips back to VISIBLE on restore is a *real* `FROZEN→ACTIVE` (or `…→ACTIVE`) transition that produces an `onChange`. If no such transition fires, `lastVisibilityState` stays at `notVisible` forever.

**Fact A3 — TWO uncoordinated restore drivers race, and the loser's path is a no-op.** On bfcache/freeze restore, two independent code paths both try to drive `FROZEN → {active|passive|hidden}`:

- **Driver 1 (container chain):** `_onResume` (`sharc-container.js:5125-5139`), bound to the `resume` event (`:5048`, registered in the constructor at `:1554`). It resolves FROZEN by `document.visibilityState` + `document.hasFocus()`: visible+focused ⇒ `_transitionToActive()`; visible+unfocused ⇒ `setState(PASSIVE)`; else `setState(HIDDEN)`. It has **no intersection signal**, so a visible-but-unfocused page resolves to **PASSIVE**, not ACTIVE.
- **Driver 2 (HTML adapter):** registered *after* the container chain (adapter `attach` runs in `load()` at `sharc-container.js:1663`, after the constructor wired the container's own listeners). The adapter wires **both** `resume` → `_onResume` (`html-adapter.js:220, 491-503`) **and** `pageshow(persisted)` → `_onPageshow` → `_transitionFromFrozen` (`html-adapter.js:457-461, 570-592`). `_transitionFromFrozen` has the **IntersectionObserver** ratio and resolves visible+intersecting≥0.5 ⇒ `setState(ACTIVE)` directly from FROZEN.

The race (audit F6, verbatim mechanism): the container's `_onResume` runs first and may resolve `FROZEN→ACTIVE` (focused) **or** `FROZEN→PASSIVE` (unfocused). Then the adapter's `_transitionFromFrozen` (driven by `pageshow`) tries `FROZEN→ACTIVE` — but the container is **no longer FROZEN** (driver 1 already moved it), so `_transitionFromFrozen` early-returns (`html-adapter.js:572`). And the adapter's `_onResume` augmentation only promotes `PASSIVE→ACTIVE` (`html-adapter.js:498`). So the surviving path can be: `FROZEN→ACTIVE` via driver 1, then driver 2's `setState(ACTIVE)` is a **no-op** (already ACTIVE) ⇒ **no second `onChange`**. Per Fact A1, this is fine *when the surviving transition is a real `FROZEN→ACTIVE`* — that DOES emit an `onChange` which drives `_signalVisibility('visible')`. The failure window is the **no-op / current-level** case: when the restore's effective destination equals the state the container already holds, so driver 2's `setState(sameState)` is a no-op and **no transition edge crosses into `active`, hence no compensating `onChange` fires** (e.g. the freeze was entered from a state where OMID was *already* `notVisible` and the restore resolves to that same level without a distinct edge into `active`). The bug is the *absence of a fresh transition*, not a transition that fails to notify. In that window `lastVisibilityState` is stuck at `notVisible`, `_signalVisibility('visible')` is never reached (Fact A1) or early-returns (Fact A2), and **OMID reports `NON_VISIBLE` for a visible ad.**

The deeper root is the one R1 named for the whole channel class: **the visibility signal is edge-triggered with no current-state replay.** A creative/extension restored *into a visible viewport* may never receive the visibility signal because no *edge* occurred — only the *level* ("we are now visible") is true, and nothing re-asserts the level.

### 1.2 Failure B — dead MessagePort (creative-side channel, port-DEPENDENT)

The ticket title and audit §2.3 flag a second, distinct problem: **bfcache closes the MessageChannel.** The per-session MessagePort is created in `SHARCCreativeProtocol.initChannel` (`sharc-protocol.js:713-731`): `new MessageChannel()` (`:715`), `port1` attached to the container (`_attachPort`, `:361-369`), `port2` transferred **once** to the creative via a bootstrap `postMessage(..., [port2])` (`:727-731`). On bfcache (`pagehide` with `persisted:true`), the browser **discards the MessageChannel** (audit §2 line 92: "MessageChannel/BroadcastChannel are closed by bfcache"; audit §2.3 / FROZEN-modeling row: "MessageChannel alive? … bfcache: NO"). On `pageshow(persisted)` restore, `this._port` still references a **dead port**: posting into it silently no-ops (the message goes nowhere; `postMessage` on a closed port throws or is dropped depending on engine — neither delivers).

**The consequence for R1:** R1's establish-push (D1) and creative replay (D3) close the late-subscriber bug *over a live channel*. But R1's own scope note is explicit (R1 §"Scope boundaries", #338): "**bfcache closes the MessagePort; a push into a dead port is lost.** R1 does not add bfcache channel-liveness (that is R3, Chrome-only)." So after a bfcache restore, R1's container→creative replay (which the **creative-side** MRAID/SafeFrame bridges depend on, and which the **OMID iframe-relay** `_relayOmidEvent` over the 0.7.7 router depends on) lands in a closed port and is lost. The publisher-page OMID `adEvents.stateChange` (Failure A) is NOT affected by this; the creative-side surfaces ARE.

### 1.3 Why these are bundled, and how R3 must treat them

Failure A is the P1 symptom (OMID NON_VISIBLE). Failure B is the channel-liveness gap that R1 deferred to R3. They are **independent mechanisms** (A is container-side/port-independent; B is the creative-side dead channel), but #338's title binds them: a complete post-bfcache-restore fix must (a) re-assert visibility *as a level* so OMID flips back to VISIBLE regardless of whether a transition edge fired, AND (b) ensure the creative-side channel is live so R1's replay actually reaches the iframe. R3 delivers both, plus removes the race that creates Failure A's window.

## 3. The R3 design decision

Three coordinated changes, ordered by the restore sequence: (3.1) coordinate the drivers into one authority, (3.2) re-assert visibility as a *level* on every restore, (3.3) detect and relink a dead port so the creative-side replay lands.

### 3.1 — Driver coordination: single restore authority (audit R4, RC-2)

**Decision:** designate **one** restore authority and have the other **yield**, mirroring the LOADING→ACTIVE strict/permissive yield already in the adapter (`html-adapter.js:538-541`).

**Who owns restore:** the **HTML adapter** (`_transitionFromFrozen`), because it has the IntersectionObserver ratio (`html-adapter.js:581-588`) and therefore the *correct* restore destination (visible+intersecting≥0.5 ⇒ ACTIVE; partial ⇒ PASSIVE; off-screen ⇒ HIDDEN). The container's `_onResume` (`sharc-container.js:5125-5139`) has only focus/visibility and resolves a visible-unfocused page to PASSIVE — the under-resolution that opens Failure A's window.

**The handoff contract (RFC-2119, §4 INV-R1..R3):** when a lifecycle adapter is attached, the container's `_onResume` MUST yield restore-destination resolution to the adapter; the container chain MUST NOT independently drive `FROZEN→{active|passive|hidden}` while an adapter owns restore. When **no** adapter is attached (e.g. a non-HTML / native-SHARC container with no IntersectionObserver), the container's `_onResume` remains the authority (it is the only driver). This is the symmetric inverse of the existing `attach`-time wiring: today the adapter *augments* the container (`html-adapter.js:491-503` only nudges PASSIVE→ACTIVE); R3 inverts the default so the adapter *owns* the FROZEN-exit destination and the container yields, exactly as the adapter already yields to the handshake in strict LOADING.

**Single ordered path (no double-drive):** on `pageshow(persisted)` / `resume`, exactly one driver computes the destination and issues exactly one `setState(destination)`. Because the destination is computed once from the authoritative (intersection) signal, the no-op-second-`setState` race disappears, and the surviving transition is a *real* `onChange` that drives the OMID visibility level (§3.2 makes this belt-and-suspenders, not load-bearing).

**Note on `pageshow` vs `resume` duplication:** the adapter wires BOTH `pageshow(persisted)`→`_transitionFromFrozen` and `resume`→`_onResume`. bfcache fires `pageshow(persisted:true)`; OS-freeze fires `resume`. They are different events but both currently reach restore logic. R3 MUST ensure that for a *single* restore, the destination is computed and applied **once** (idempotent: if `_transitionFromFrozen` already left FROZEN, a subsequent `resume`-driven path is a no-op — but per §3.2 the no-op no longer drops the visibility level).

### 3.2 — Level-triggered visibility replay on restore (RC-1; consistent with R1's replay-on-subscribe)

**Decision:** on a confirmed bfcache/freeze **restore**, the container MUST re-assert the **current** visibility *level* to extensions and to the creative channel, **independent of whether a state-machine transition edge fired.** This is the bfcache-restore analogue of R1's D1 establish-push (R1 §D1) and the contract's INV-4 (establish completeness): R1 pushes the *current state* when a session establishes; R3 pushes the *current state* when a session **restores**. Same philosophy — deliver the level, not just the edge.

**Mechanism (level re-assert), two reach points:**

1. **Extension reach (fixes OMID Failure A directly):** after the single restore authority (§3.1) has resolved the post-restore state, the container MUST notify extensions of the **current** state even if `setState` was a no-op (already in that state). The cleanest seam that does NOT weaken the existing `onChange`-on-real-transition semantics is a **restore-scoped re-assert**: a dedicated container method (e.g. an internal `_reassertCurrentStateAfterRestore()`) that calls `_notifyExtensionsLifecycle('stateChange', { newState: current, previousState: current, restored: true })` once, post-restore, when `current` is a creative-queryable non-`loading` state. The OMID bridge's `onContainerStateChange('active')` then reaches `_signalVisibility('visible')`; the OMID-side `lastVisibilityState` guard (`:1158`) keeps it idempotent (if OMID is *already* VISIBLE, no duplicate fires — exactly the contract's dedup discipline). **This is OMID's level-replay; it is the load-bearing fix for the P1 symptom and is entirely publisher-page (no port dependency).**

2. **Creative-channel reach (fixes the creative-side bridges + OMID iframe relay):** the same restore event MUST drive a container→creative `sendStateChange(currentState)` so MRAID `viewableChange`/SafeFrame `geom-update`/OMID iframe-shim relay re-sync — **but this only lands if the port is live**, which is exactly RC-3 / §3.3. So §3.3 is a precondition for reach point 2; reach point 1 stands alone.

**Consistency with the contract's dedup (INV-1, §3 of the contract):** the contract's send-layer dedup suppresses an **identical consecutive** sent state. On restore, the last *sent* state before freeze was typically `frozen` (or `hidden`→`frozen`), so a post-restore `active`/`passive` is a **distinct** value and is NOT deduped (contract INV-2/INV-10, the consecutive-only rule, E9 "freeze→restore" row). The level re-assert therefore composes cleanly with the dedup: it does not introduce a double, and it is not wrongly suppressed. R3 MUST verify the per-session `_lastSentState` is in the right state across a restore (it is per-session and survives in-memory across bfcache since the container JS object is parked, not destroyed — but the *port* it sends through is dead; see §3.3 ordering).

**Why level-triggered, not "just fire an edge":** synthesizing a fake `FROZEN→ACTIVE→…` edge would emit spurious transient states (the phantom-HIDDEN class, audit NEW-B) and would lie about the transition history. Level re-assert delivers the *truth* ("current state is active") exactly once, which is what every consumer actually needs and what R1 established as the correct shape for this channel class.

### 3.3 — Dead-port detection + relink protocol (RC-3; audit R3/NEW-E)

**Decision:** on a confirmed bfcache restore (`pageshow` with `persisted:true`), before the container relies on the creative channel for reach point 2 (§3.2), it MUST verify the MessagePort is **live**; if dead, it MUST re-establish the channel (relink) or fail cleanly, and it MUST NOT emit state into a closed port.

**Detection — how the container learns the port is dead.** There is no synchronous `port.isClosed` API. Three candidate detection strategies, in preference order; the build phase selects one with a Chrome/Puppeteer probe (jsdom cannot model port closure):

- **D-a (restore-signal-driven, PREFERRED):** treat `pageshow(persisted:true)` as the authoritative "the channel is presumed dead" signal. bfcache *always* discards the MessageChannel, so a persisted pageshow ⇒ relink unconditionally. No round-trip probe needed; deterministic. This is the simplest correct rule and aligns with the audit's "the bfcache/OS-freeze distinction is load-bearing here" (audit R3): bfcache restore ⇒ relink; OS-freeze `resume` ⇒ port survived ⇒ no relink. **Recommendation: D-a.**
- **D-b (liveness ping):** post a `Container:ping` and await a `Creative:pong` with a short timeout; on timeout, treat as dead and relink. More general (covers non-bfcache port death) but adds a round-trip, a timeout to tune, and a new message pair — and a new message pair is a **wire addition** (STOP-AND-ASK). Not recommended for R3's scope.
- **D-c (error-driven):** attempt the send and catch the throw. Unreliable — a closed `MessagePort.postMessage` does not uniformly throw across engines (it can silently drop). Rejected.

**Relink protocol (how the channel is re-established without violating the 0.7.7 trust model).** The relink re-runs the *existing* bootstrap, scoped to the existing placement session:

1. The container creates a **new** `MessageChannel`, attaches the new `port1` (`_attachPort`, replacing the dead `this._port`), and transfers the new `port2` to the creative via the **existing** bootstrap `postMessage(handshake, targetOrigin, [port2])` path (`sharc-protocol.js:713-731`). The handshake carries the **same** `placementSessionId` (the placement session did not end — the page was parked, not navigated away).
2. The creative iframe (which also restored from bfcache) re-receives the bootstrap and re-attaches its `port2`. The creative's `sessionId` is **unchanged** (same placement session), so the existing session-gate (`sharc-protocol.js:494-501`) continues to validate inbound messages against the same `sessionId` — **no session-identity change, no new trust grant.**
3. After relink, the container issues the §3.2 reach-point-2 `sendStateChange(currentState)` over the **new, live** port. R1's creative-side replay (D3) and the bridges re-sync exactly as on first establish.

**The 0.7.7 router interaction — the one thing to flag.** The 0.7.7 router owns the publisher-side `window` message listener (`sharc-protocol-router.js:98`), which **survives bfcache** (it is re-registered on the restored page's `window`, or persists with the parked document and resumes). Per-protocol nonces are derived via HMAC over `(rootNonce, prefix + ':' + placementSessionId)` (`sharc-protocol-router.js:11, 384-393`). Because relink reuses the **same `placementSessionId`**, the **same nonces remain valid** — the router does NOT need to re-mint. **However**, the router already exposes `rederiveAllProtocolNonces()` (`sharc-protocol-router.js:241-254`, built for sequential-impression re-mint, RTR-D21) as a re-arm primitive. R3 has a choice:

- **Relink WITHOUT router re-mint (PREFERRED):** the MessageChannel bootstrap (`SHARCCreativeProtocol.initChannel`) is the protocol-port transport; it is **separate** from the router's `window`-message OMID/diagnostics relay. Re-running `initChannel` re-establishes the per-session creative port without touching router nonces (the placementSessionId and thus the derived nonces are unchanged). This is a **transport re-establishment, not a wire/protocol change** — no new message type, no nonce change, no trust-model change. **Recommendation: relink the creative MessagePort via the existing `initChannel` bootstrap; do NOT re-mint router nonces.**
- **Relink WITH router re-arm:** if the OMID iframe-relay (router-based) also needs its `onReady`/derivation re-fired post-restore (because the iframe shim was discarded with the bfcached document and must re-register), call `rederiveAllProtocolNonces()`. This is the *existing* sequential-impression mechanism reused — but invoking it on restore is a behavioral interaction worth ratifying because it re-fires `onReady` for every registered protocol. **STOP-AND-ASK** (§9 item 3): does the OMID iframe shim survive bfcache (it is in the creative iframe, which is also bfcached), and if it must re-register, is reusing `rederiveAllProtocolNonces()` on restore acceptable, or does it need a restore-specific re-arm?

**STOP-AND-ASK — wire/protocol/security implications (do NOT silently design a wire change):** the PREFERRED relink (D-a detection + `initChannel` re-bootstrap, same `placementSessionId`, no new message type, no nonce re-mint) is assessed as **NOT a wire change and NOT a trust-model change** — it re-runs the existing bootstrap transport over the existing session identity. **But this assessment touches the MessagePort security model and the 0.7.7 router, so it is flagged for Jeffrey's explicit ratification (§9 items 2–4) rather than assumed.** If the build phase finds that detection D-b (a ping/pong pair) or router re-mint is actually required, that IS a wire/protocol change and MUST stop and return to Jeffrey before any code.

## 4. RFC-2119 invariants (R3 restore/relink/replay)

In the style of the State-Delivery Contract's INV-1..INV-23 (which R3 MUST NOT violate). These are the new R3 invariants; numbered INV-R1..INV-R12 to avoid collision.

**Driver coordination (§3.1):**

> **INV-R1 (Single restore authority).** On a restore from FROZEN, the container MUST resolve the post-restore destination through **exactly one** authority. When a lifecycle adapter is attached, that authority MUST be the adapter (it holds the intersection signal); the container chain's `_onResume` MUST yield. When no adapter is attached, the container chain MUST be the authority.

> **INV-R2 (Exactly-one restore transition).** A single restore event MUST produce **at most one** `setState(destination)` from FROZEN. Two drivers MUST NOT both issue a FROZEN-exit transition for the same restore. A second driver observing the container already out of FROZEN MUST no-op.

> **INV-R3 (Correct destination).** The restore destination MUST reflect the authoritative visibility signal: visible + intersecting ≥ threshold ⇒ ACTIVE; visible + partially intersecting ⇒ PASSIVE; otherwise HIDDEN. A visible-into-viewport restore MUST NOT under-resolve to PASSIVE/HIDDEN when the intersection signal supports ACTIVE.

**Level-triggered visibility replay (§3.2):**

> **INV-R4 (Level re-assert on restore).** On a confirmed restore, the container MUST re-assert the current lifecycle level to registered extensions exactly once, **regardless of whether the restore produced a state-machine transition edge** (i.e. even if `setState` was a no-op because the destination equals the pre-freeze state). This re-assert MUST carry the current creative-queryable state and MUST be marked as a restore re-assert (so consumers can distinguish it from a fresh transition if they need to).

> **INV-R5 (OMID visibility correctness post-restore).** After a restore into a visible viewport, the OMID bridge MUST report `VISIBLE` (`adEvents.stateChange('VISIBLE')`), and after a restore into a non-visible state it MUST report `NON_VISIBLE`. The OMID-side `lastVisibilityState` dedup (`sharc-omid-bridge.js:1158`) MUST keep this idempotent: if OMID already holds the correct level, no duplicate signal fires.

> **INV-R6 (Replay never fabricates intermediate edges).** The restore level re-assert MUST NOT synthesize spurious intermediate transitions (e.g. a phantom `HIDDEN` or a fake `FROZEN→ACTIVE` walk) to provoke an edge. It MUST deliver the current level directly. (Preserves the audit's NEW-B concern; does not regress it.)

> **INV-R7 (Non-`loading`/queryable only).** The restore re-assert MUST only deliver a creative-queryable state (`ready`/`active`/`passive`/`hidden`/`frozen`). It MUST NOT deliver `loading` or `terminated` (consistent with contract INV-12).

**Dead-port detection + relink (§3.3):**

> **INV-R8 (No emit into a dead port).** On a bfcache restore (`pageshow` with `persisted:true`), the container MUST NOT `sendStateChange`/`_sendMessage` into the pre-freeze MessagePort without first establishing that the port is live or relinking it. A send into a known-dead port MUST be suppressed (no silent loss treated as success).

> **INV-R9 (Relink preserves session identity).** A relink MUST reuse the existing `placementSessionId` and MUST NOT change the creative's `sessionId`. The session-validation gate (`sharc-protocol.js:494-501`) MUST remain unchanged and MUST continue to validate post-relink messages against the same `sessionId`. (No new trust grant; per-session isolation, contract INV-20/INV-22, preserved.)

> **INV-R10 (Relink is transport-only by default).** The default relink MUST re-establish the per-session MessagePort via the existing bootstrap (`initChannel`, `sharc-protocol.js:713-731`) and MUST NOT introduce a new message type, a new envelope field, or a router nonce re-mint. Any deviation (a ping/pong probe pair, a router re-derivation on restore) is a wire/protocol change and MUST be ratified before implementation (§9).

> **INV-R11 (Post-relink replay).** After a successful relink, the container MUST deliver the current lifecycle state over the new live port (the §3.2 reach-point-2 `sendStateChange(currentState)`), so creative-side bridges (MRAID/SafeFrame) and the OMID iframe relay re-sync via R1's replay (D1/D3). This delivery MUST respect the contract's send-layer dedup (INV-1) against the per-session `_lastSentState` as reset/seeded for the relinked session.

> **INV-R12 (Clean failure).** If a relink cannot be completed (creative iframe did not re-receive the bootstrap, or relink times out), the container MUST fail cleanly — it MUST NOT leave a half-open channel, MUST NOT throw into the page, and SHOULD surface the failure through the existing container error/diagnostics path rather than emitting into a dead port. The publisher-page OMID visibility re-assert (INV-R4/R5) MUST still succeed independently of relink outcome (it does not depend on the port).

**Invariant count: 12 (INV-R1 … INV-R12).**

**Tensions called out explicitly:**

- **T1 — Driver-authority inversion is a behavior change.** Today the adapter *augments* the container's restore (`html-adapter.js:491-503`); R3 makes the adapter *own* it and the container *yield*. For the common case the destination is the same (or strictly better — INV-R3 fixes the under-resolution). But any operator/test asserting the container-chain restore path drives independently would see a change. This is the intended fix (RC-2), flagged for ratification (§9 item 5).
- **T2 — Audit R2/NEW-B (phantom HIDDEN / direct ACTIVE→FROZEN edge) is closed by #340 (PR #353), which lands earlier in this batch.** Freeze *entry* from ACTIVE/PASSIVE now takes the direct edge (no phantom `HIDDEN`), and the bf-2 Puppeteer contract was retargeted accordingly in #340 — so the earlier framing of NEW-B as "open / freeze entry still walks `…→HIDDEN→FROZEN`" is superseded by the time R3 builds. R3 governs *restore*, not *entry*, and is independent of the entry-edge change either way — it reads the *current* level whatever the entry path was. The two simply touch different halves of the freeze lifecycle (entry vs restore); no conflict.
- **T3 — Detection strategy is build-time-selected.** §3.3 recommends D-a (`pageshow persisted` ⇒ relink unconditionally), but the final choice needs a Chrome/Puppeteer probe (jsdom can't model port closure). If D-a proves insufficient (e.g. a port that dies *without* a persisted pageshow), the fallback to a ping/pong probe IS a wire change and returns to Jeffrey (INV-R10 / §9).

## 7. Security

- **No new trust grant, no new observability.** Relink reuses the existing `placementSessionId` and `sessionId` (INV-R9); the session gate (`sharc-protocol.js:494-501`) is unchanged. A relinked creative receives only its **own** lifecycle state — no cross-placement path (contract INV-20/INV-22 preserved). The 0.7.7 router nonces are unchanged in the default path (same `placementSessionId` ⇒ same HMAC derivation; root nonce never on the wire).
- **The relink does not re-open a trust window.** The new `port2` is transferred to the **same** creative iframe origin via the **same** bootstrap `postMessage(..., targetOrigin, [port2])` path (`sharc-protocol.js:727-731`) that established the original channel. No widening of `targetOrigin`, no new message type, no new accepted sender.
- **bfcache-restore is the trigger, not an attacker-controllable surface.** `pageshow{persisted:true}` is a browser-dispatched event; a page cannot forge another origin's restore. The relink is initiated by the container on its own page.
- **Publisher-page OMID path is unaffected by the port.** Failure A's fix (level re-assert ⇒ `adEvents.stateChange`) runs entirely on the publisher page against the OM SDK AdSession; it crosses no frame boundary and adds no message surface.

## 8. Consequences

**Easier:** #338/NEW-C closes at root (level-triggered visibility, not edge-only); the double-driver race (RC-2) is eliminated by single authority; the dead-port gap R1 explicitly deferred (RC-3) is closed; R1's replay finally lands post-bfcache (creative-side bridges re-sync); OMID viewability stops under-counting after bfcache round-trips; the bfcache-vs-OS-freeze distinction becomes load-bearing in exactly one place (relink), as the audit prescribed.

**Harder / accepted:** the driver-authority inversion (T1) is a behavior change requiring ratification; the dead-port half can only be proven at the Puppeteer/Chrome tier (jsdom blind spot — the same caveat the audit attaches to R3); a relink adds a restore-time re-bootstrap cost (one MessageChannel + one postMessage per bfcache restore — negligible, once per restore); the OMID iframe-shim survival across bfcache (does it need re-registration?) is an open question that may pull in the router re-arm (STOP-AND-ASK 3); audit R2/NEW-B (phantom HIDDEN) remains open and adjacent (T2).
