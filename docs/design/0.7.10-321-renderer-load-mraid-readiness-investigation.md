# Discover: #321 — renderer 2114 termination + MRAID readiness (root-cause investigation)

**Issue:** [#321](https://github.com/jeffreycarlson/SHARC/issues/321)
**Date:** 2026-06-06
**Pairs with design doc:** `0.7.10-renderer-lifecycle-readiness-compat-creatives.md` (the ADR — decisions live there)
**Method:** faithful e2e harness — real `sharc-container.mjs` + real `examples/renderer/index.html`, cross-origin, CSP-correct serving, headless Chromium (puppeteer-core), real private DV creatives. "Trust but verify" — this refuted three of my own theories before landing the cause.

---

## Trigger / symptom
Visual DV spot-check: a real inline/MRAID-flavored `adm` creative **rendered visually and DV OMID completed, but the container terminated** with `RENDERER_TIMEOUT` (2114, `reason: rendered_reply`). #321 was filed framing this as *"renderer readiness is too DCL-centric — make it API-specific (SHARC/MRAID/SafeFrame/HTML)."* **That framing is wrong** (see Corrected understanding).

## What we ruled out — and how (the valuable part)
Each was tested, not argued:

1. **"DCL fires too early/late" / wrong lifecycle event** — REFUTED. In the faithful harness `readyState` is `complete` at the backup checkpoint, the backup microtask arms, and `:rendered` posts in <10ms regardless of creative DOM timing.
2. **Dead primary DCL listener** (`examples/renderer/index.html` ~L1432) — REAL but not the cause. `document.open()` removes all document listeners per spec (the L1429 "survives document.open" comment is factually wrong), so the primary listener is dead — but the L1437 backup microtask compensates. Not the 2114.
3. **Async preamble** (bridge dynamic-import + OMID shim `fetch`) blocking `:rendered` — REFUTED. Injecting 3s then 5s latency into those responses moved `:rendered` by ~0ms; the bridge load is non-blocking (probe-and-skip), and `:rendered` posts via the backup microtask before the awaits resolve.
4. **100ms `loadAck` deadline false-positive on a busy main thread** — REFUTED. A 600ms busy-loop in the creative's `load` handler did NOT trip it (the iframe-element `load` fires after the creative's load handlers finish, so the probe arrives when the thread is free).
5. **The CSP-header artifact (key lesson)** — every 2114 in my *throwaway* harnesses was a **missing CSP response header**, not a SHARC defect. The container sets the iframe `csp="object-src 'none'; base-uri 'none'"` (RENDERER_IFRAME_CSP); Embedded-Enforcement blocks the frame unless the renderer response carries a matching CSP header. `python -m http.server` sends none → frame never loads → false 2114. With a CSP-correct static server the render handshake is robust. **Do not conflate serving config with a SHARC race.**
6. **OMID no-subscription** — that's a measurement-window issue (#244, external verification not subscribing in the settle budget), not a render/load race. `creativeRendered:true`, `terminated:false` in the automated report.

## Confirmed root cause #1 — the load-event re-entry race (Sequence 1)
`_wireRendererProtocol`'s iframe `load` handler (`src/sharc-container.js` ~L2394) guards only on `this._terminated` — **no `creativeRendered` check**. A real creative's external ad scripts navigate / `document.open`+`write` the renderer iframe ~1s in, firing a SECOND `load`. The handler re-enters the entire handshake: re-runs injectors, re-transitions the router to `attaching-renderer`, re-posts `:render`, and **re-arms `rendererReply`** (~L2508). The reloaded document is no longer the SHARC renderer → no second `:rendered` → the re-armed timeout fires → 2114, killing a creative that already reached `active`.

**Smoking gun (faithful e2e):** iframe `load` events at **[9ms, 1019ms]**; container `active` at ~13ms; **2114 at 9024ms ≈ 1019 + 8000ms (`rendererReply`)**. A trivial creative with no second load reaches `active` clean. The validator's automated report shows these as `creativeRendered:true/terminated:false` **only because it snapshots at ~3s — before the 8s timeout fires.**

## Confirmed root cause #2 — MRAID backward-compat gap (Sequence 2)
The MRAID readiness chain (`src/sharc-mraid-bridge.js`): `ready` + `getState()==='default'` fire in `SHARC.onReady` (~L405, on `Container:init`); `isViewable()`/`viewableChange(true)` fire in `SHARC.on('stateChange')` (~L466, `_isViewable=(state==='active')`). So: `:rendered` → 200ms bootstrap → `createSession` → `Container:init` (→ready) → container `active` → `stateChange('active')` (→isViewable).

The bridge is **a pure adapter over `window.SHARC`** and requires the SHARC creative SDK in the creative iframe. A **raw MRAID ad ships no SHARC SDK** → no `window.SHARC` → no `createSession` → no `Container:init` → mraid never reaches `ready` → **stall**. Harness probe confirmed: a raw creative returned **`NO_MRAID`** (the bridge↔SDK provisioning is something the *validator* injects; production raw tags have nothing). The renderer today injects the OMID shim + bridge *module* but **not** the creative SDK (it assumes the SDK is in the markup — comments ~L198/L947).

## Corrected understanding of #321
Render readiness (`:rendered` on inner DCL) is **robust** — the creative reached it (that's why OMID completed). The real defects are:
- **(a)** the post-render load-event re-entry race [Sequence 1], and
- **(b)** the backward-compat MRAID wrapper that lets a SHARC-unaware ad run as if in an MRAID-only container [Sequence 2].
API-specific *readiness signals* (mraid-ready/safeframe-ready as alternate acks) are NOT required and are out of scope.

## Product intent (Jeffrey, ratified)
SHARC is the **hub** controlling several APIs; goal is to move the industry to a SHARC-only world while staying backward compatible. The container maps/translates **SHARC↔MRAID bidirectionally**. A legacy MRAID creative runs inside the SHARC container **as if it were an MRAID-only container** — unmodified, zero SHARC awareness, ships no SDK. The compat layer is a **self-contained wrapper** the renderer applies (gated on the `bridges` field): MRAID API inward, SHARC normalized outward. **Ratified mechanism:** the wrapper *drives* the SHARC handshake on the ad's behalf (the init handshake is NOT disabled; the wrapper performs it). Renderer-side wrapper provisioning is in scope for 0.7.x.
