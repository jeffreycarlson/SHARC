# ADR: Renderer-protocol load-listener idempotency + compatibility-creative readiness contract

**Issue:** [#321](https://github.com/jeffreycarlson/SHARC/issues/321) (reframed — see Decision 4)
**Status:** Accepted — ratified 2026-06-06 (Jeffrey): Decision 3 follows the **wrapper-drives-the-handshake** model (the wrapper performs the SHARC handshake for the wrapped ad; the init handshake is NOT disabled). Renderer-side wrapper provisioning is **in scope for 0.7.x**.
**Date:** 2026-06-06
**Baseline:** 0.7.7 cross-frame protocol router (`docs/design/0.7.7-cross-frame-protocol-router.md`)

## Context

A real inline/MRAID-flavored `adm` creative rendered visually, DV OMID completed, the container reached `active` — and then terminated at ~9s with `RENDERER_TIMEOUT` (2114, `reason: rendered_reply`). #321 read this as "renderer readiness is too DCL-centric; make it API-specific per creative type." **That framing is wrong.** The creative reached DCL fine — that is *why* `:rendered` arrived and the container went active. The 2114 has a different root cause.

**Sequence 1 — the load-event re-entry race (confirmed, empirical).** `_wireRendererProtocol`'s iframe `load` handler (`src/sharc-container.js` ~L2394) guards only on `this._terminated` — there is **no `creativeRendered` check**. A real creative's external scripts navigate / `document.open`+`write` the renderer iframe ~1s in, firing a SECOND `load`. The handler re-enters the *entire* handshake: re-runs injectors, re-transitions the router to `attaching-renderer`, re-posts `:render`, and **re-arms `rendererReply`** (`_startTimeout('rendererReply', …)` ~L2508). The reloaded document is no longer the SHARC renderer → no second `:rendered` → re-armed timeout fires → 2114. Faithful cross-origin CSP-correct e2e: iframe loads at [9ms, 1019ms]; `active` at ~13ms; 2114 at 9024ms ≈ 1019 + 8000. A trivial creative with no second load reaches `active` clean.

This is precisely the surface 0.7.7 already split into two listeners: the render-wiring path (`_wireRendererProtocol`) for the *first* load, and the navigation backstop (`_armRendererBackstop`, armed in `_onRendererRendered` ~L3157) for *post-render* loads. The race is that the first listener was never told to stand down once `creativeRendered` is true — so both listeners fire on the second load, and the render-wiring path wins by re-arming a timeout the backstop never intended to exist.

**Sequence 2 — MRAID readiness chain (confirmed structurally).** In `src/sharc-mraid-bridge.js`: mraid `ready` + `getState()==='default'` fire in `SHARC.onReady` (~L405, on `Container:init`); `isViewable()=true` + `viewableChange(true)` fire in `SHARC.on('stateChange')` (~L466) where `_isViewable=(sharcState==='active')`. So the chain is `:rendered` → 200ms MessageChannel bootstrap → `createSession` → `Container:init` (→`ready`) → container reaches `active` → `stateChange('active')` delivered → `isViewable`. `ready` is strictly downstream of `:rendered`; `isViewable` requires the container to deliver `stateChange('active')`. The bridge is a pure adapter over `window.SHARC` and **requires the SHARC creative SDK in the creative iframe** — raw MRAID ad tags do not ship it (the validator injects it).

**Ruled out** (do not design against): the backstop's 100ms loadAck deadline is not a busy-main-thread false positive (600ms busy-loop did not trip it); OMID is out of scope; every other 2114 in throwaway harnesses was a missing-CSP-header serving artifact (Embedded-Enforcement on `csp="object-src 'none'; base-uri 'none'"` ~L126/L1914), not a handshake defect. The render handshake itself is robust.

## Decision

1. **Render-protocol load-listener idempotency (the fix).** The `_wireRendererProtocol` load handler MUST short-circuit once the handshake is complete: add `if (this.creativeRendered) return;` immediately after the existing `if (this._terminated) return;` (~L2401). **Contract:** the render-wiring path owns the *first* load only; every subsequent iframe `load` is owned exclusively by the navigation backstop (`_armRendererBackstop`). Post-render loads must never re-run injectors, re-transition the router, re-post `:render`, or re-arm `rendererReply`. This is *within* the renderer-protocol implementation and does not touch the router — **baseline-consistent.** (It also tightens 0.7.7's `attaching-renderer → rendered` phase model in code: a second `transitionTo('attaching-renderer')` after `rendered` is illegal and this guard prevents it.)

2. **Post-render second-load policy (tolerate same-origin reopen; 2118 only on cross-document navigation).** Once Decision 1 routes the second load to the backstop, the backstop's existing `verifyFirstLoad` loadProbe/loadAck round-trip (100ms deadline, ~L4391) is the decision point. A legitimate compatibility creative's **same-origin `document.open`/`write` reopen re-injects the renderer prelude, which answers the loadAck** → tolerated (no 2118). A **cross-document navigation cannot answer** (different document, no prelude) → `RENDERER_UNAUTHORIZED_NAVIGATION` (2118). The loadAck prelude lives in the *same document*, so genuine reopen vs. cross-document navigation are distinguishable by exactly this probe — no new mechanism is needed. **Policy decision:** same-origin reopen is *tolerated*, not flagged. This is the real, narrowly-scoped version of #321's "API-specific" instinct: applied to post-render *navigation* policy, not renderer *readiness*. **Back-compat:** behavior change is observable only for creatives that today trip 2118 via reopen — those are currently false-terminated, so this is a strict improvement, no legitimate creative regresses. Plain-HTML and native-SHARC creatives that never reopen are unaffected. **STOP-AND-ASK (Jeffrey):** if the backstop's `verifyFirstLoad` is currently armed *only* on the Markup `:rendered` path (it is — `_onRendererRendered` passes `{verifyFirstLoad:true}`) but a future change wants the URL variant to also tolerate reopen, that widens the backstop contract — flag before implementing.

3. **MRAID compatibility wrapper + non-SHARC handshake-mode switch (the linchpin).** A raw MRAID ad ships NO SHARC SDK, so it NEVER calls `createSession`. Today the container's strict default (`requireSharcInit: true`, ~L1599) arms `_startSessionTimeout` and waits for a handshake the ad cannot drive → no `Container:init` → mraid never reaches `ready` → stall. The fix has two halves:

   - **(a) Renderer-applied, self-contained wrapper.** When `bridges` is present (container detection: `options.bridges` → `creativeMeta.apis` AdCOM codes → adm scan, 0.7.1), the renderer wraps the raw ad with a self-contained bundle — `sharc-protocol` + `sharc-creative` + `sharc-mraid-bridge`, provisioned by the renderer, NOT shipped by the ad and NOT a separately-injected SDK the ad must reference. **Inward** the wrapper presents the full `window.mraid` API (getState/isViewable/addEventListener; ready/stateChange/viewableChange; open/expand/resize/close) so the ad runs unmodified. **Outward** it owns the SHARC-side protocol: the bundled `sharc-creative` drives `createSession` on DCL (~L176-194) — *the wrapper, not the ad, initiates the handshake.* The existing readiness chain is unchanged and correct: `Container:init`→`SHARC.onReady`→mraid `ready`+`default` (bridge ~L405); container→`active`→`stateChange('active')`→`isViewable`/`viewableChange(true)` (bridge ~L466, `_isViewable=(state==='active')`). Bidirectional mapping reuses the shipped adapter (e.g. `mraid.open`→`requestNavigation`; SHARC→MRAID via the same handlers). `bridges` absent → native-SHARC creative ships its own SDK, unchanged.

   - **(b) Lifecycle-mode switch on detection.** For a `bridges`-present creative the container does NOT disable the handshake — it expects the WRAPPER to drive it. So `requireSharcInit` stays effectively `true` and the existing strict path / `HtmlAdapter` yield-to-handshake logic (`_maybeAdvanceToActive` ~L401) is REUSED unchanged: init→ready and active→isViewable are owned by the wrapper's `createSession`→`Container:init`→`stateChange` chain, exactly as for a native creative. **No new lifecycle mode and no router/wire-format change is required** — the only behavioral change is *where the SDK comes from* (renderer-provisioned vs ad-shipped). A future MraidLifecycleAdapter (roadmapped alongside the shipped HtmlAdapter) is NOT needed for this contract; flag if one is later proposed. **Back-compat (pre-1.0):** native-SHARC and plain-HTML paths are byte-for-byte unaffected; the only new behavior is that a raw MRAID tag — which stalls today — now renders. Strict improvement, no regression.

   - **Budgets:** `ready` = `:rendered` + 200ms bootstrap + one `Container:init` round-trip, fired synchronously in `SHARC.onReady`, never before `:rendered`. `isViewable`/`viewableChange(true)` gated on the container delivering `stateChange('active')`; flips true exactly on that delivery, fires once.

   - **RATIFIED (Jeffrey, 2026-06-06):** (i) renderer-side wrapper provisioning IS in scope for 0.7.x — the renderer SHALL provision the full self-contained bundle (`sharc-protocol` + `sharc-creative` + `sharc-mraid-bridge`) for `bridges`-present creatives, before the creative's first script, so a raw no-SDK MRAID tag runs transparently. Raw-MRAID compat is a production capability, not validator-only. **Standing guard:** (ii) any future variant that flips `requireSharcInit:false` for compat creatives (letting the HtmlAdapter drive `LOADING→ACTIVE` without a handshake) changes who owns init→ready and contradicts the wrapper model — flag before implementing.

4. **Correct #321 on the record.** Render readiness (`:rendered` on inner DCL) is **robust** — the visually-rendered creative reached it. The real defects are (a) the load-event re-entry race (Decision 1) and (b) the compatibility readiness/navigation contract (Decisions 2–3). API-specific *readiness signals* (mraid-ready / safeframe-ready as alternate acks) are **not** required to fix the reported 2114 and are explicitly out of scope for this ADR; #321's acceptance criteria that hinge on alternate ack signals should be reframed against this finding.

## Consequences

**Easier:** the reported 2114 disappears with a one-line guard; the two-listener model from 0.7.7 becomes correct-by-construction; false-positive 2118s on legitimate reopen go away; the MRAID readiness sequence becomes a pinned contract with explicit timing budgets.

**Harder / costs:** Decision 3's core contract — a raw MRAID tag that ships NO SHARC SDK reaches `ready`/`isViewable` *because the renderer-provisioned wrapper drives the handshake* — is NOT node-expressible: in node there is no real renderer to provision the bundle and no real `createSession` round-trip, so the no-SDK provisioning fact cannot be asserted without faking the very thing under test. It is a validator/puppeteer contract with real renderer-side wrapper provisioning. Node can only pin the *adapter sequence* (init→ready, active→isViewable) given the wrapper is already installed — that is the regression-guard half. The `examples/renderer/index.html` ~L1429 hygiene issue (dead-ish DCL listener + factually wrong "survives document.open" comment — `document.open` removes all document listeners per spec; the backup microtask compensates today) is noted as a separate follow-up, not part of this fix.

**Baseline-consistency summary:** Decision 1 is fully within the renderer-protocol implementation (no router change) — consistent. Decisions 2–3 touch the lifecycle/handshake surface and carry the STOP-AND-ASK flags above. Decision 3 deliberately REUSES the strict handshake path and the shipped adapter rather than adding a lifecycle mode — it changes SDK *provenance* (renderer-provisioned wrapper), not the 0.7.7 router contract or the SHARC creative-protocol wire format. Neither decision silently redesigns the router.
