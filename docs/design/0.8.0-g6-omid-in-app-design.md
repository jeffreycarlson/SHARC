# ADR: G6 OMID In-App Design + Host Lifecycle INPUT

## Context

G6 is the last gate: "one creative, served anywhere — web and in-app" is unproven until the
container runs inside SDKs (`2026-06-10-sharc-1.0-definition-of-done.md` §G6). The ratified
"how": the **same JavaScript container runs inside the WebView — never a native port**. Native
integrates through (a) the L1 Native Host Interface (`2026-07-03-l1-native-host-integration-surface.md`,
ACTIONS + INPUTS, C1–C9/S1–S3) and (b) a new **app lifecycle adapter** on the
`src/lifecycle-adapters/` seam built for exactly this.

The DoD named one hard design question requiring its own doc: **OMID in-app** — the OM SDK is
native on iOS/Android and the AdSession machinery lives native-side, not on a publisher page.
Discovery (closed 2026-07-08) resolved hop-2 favorably: the OM SDK's **JavaScriptSessionService**
([iOS](https://docs.iabtechlab.com/omsdk-1.5/ios/Classes/OMIDJavaScriptSessionService.html),
[Android](https://interactiveadvertisingbureau.github.io/Open-Measurement-SDKAndroid/)) lets the
WebView's JS session client own start/finish while the native side is a signal provider created
with the WebView (`isHtmlAdView:true` → the ad view IS the WebView frame). SHARC's host-page
`OmidCompatBridge` therefore keeps AdSession ownership, and hop-1 (creative iframe → host page via
the 0.7.8 bridge/shim) ships byte-identical to web. **In-app OMID is wiring, not invention** —
this doc specifies the wiring and the three open verdicts.

Ratified sequencing: this design doc + an iOS-first harness-skeleton spike in parallel → app
lifecycle adapter → both harness apps → OMID proof. Harness apps live in-repo
(`examples/host-apps/`). Simulator/emulator runs gate; real devices are manual. Honest minimum
for the gate: G5 fixture suite identical-verdicts + expand/collapse round-trip + a stratified
50–100-row MRAID corpus sample row-by-row through the existing fail-closed compare tool
(`tools/creative-validator/src/regression.js`) + the named **port-exfiltration-across-navigation
must-test** (post-nav probe undelivered to an exfiltrated worker-held port → 2118) on both
platforms.

**Builds on (does NOT redesign):** `docs/design/0.7.8-omid-spec-compliant-bridge.md` (the
relay/shim architecture, §4.3 nonce trusted-injection, Risk R1 / `omid-finishing` grace),
`2026-06-20-slice-c-effective-visibility-composer.md` + `2026-06-20-slice-c-inapp-rawinput-reconciliation.md`
(composer, axis-3 host-wins), the NHI ADR (surface contract). Primary sources are cited inline;
each claim is marked **documented** (verbatim-verified this pass), **documented-cited** (stable
platform behavior, reference URL given, page is JS-rendered and not verbatim-extracted this
pass), or **inferred** (our reasoning; stated as such).

## Decision 1 — OMID service-script mode (the load-bearing unknown)

### 1.1 What the primary sources actually say

The OM SDK has **two different service-script builds** with different authority models:

- **In-app JS service** (`omsdk-v1.js`, shipped inside the native SDK / fetched from the
  integrator's CDN): the central event collector that bridges the WebView JS layer to the
  native SDK. **Documented** (OMID API v1.5, pp.13–14,
  [PDF](https://iabtechlab.com/wp-content/uploads/2024/08/OMID_API_v1.5.pdf)):
  > "For HTML ad sessions each integration partner is responsible for ensuring that the OM SDK
  > JS service has been injected into the WebView prior to any additional JS components."
  Injection strategies are server-side (ad server prepends the script content — "the recommended
  OM SDK JS service injection solution") or client-side via the native `ScriptInjector` /
  `OMIDScriptInjector` utilities (Android guide §webview-inject-omid; iOS guide,
  [compliance.iabtechnologylab.com/integration-guide/ios](http://compliance.iabtechnologylab.com/integration-guide/ios/)).
- **Web service** (`omweb-v1.js`, OM SDK for Web): "a standalone JS binary that performs
  measurement and manages verification scripts" — it owns measurement entirely in JS, no native
  layer exists. **Documented**
  ([Open-Measurement-SDKJS](https://interactiveadvertisingbureau.github.io/Open-Measurement-SDKJS/)),
  including: "Integrations *must not* concatenate or compile the Service Script into other
  scripts."

The session client (`omid-session-client-v1.js`) is the same library in both worlds — "used by
integration partners to perform ad session activities in the JavaScript layer"
([Open-Measurement-JSClients](https://github.com/InteractiveAdvertisingBureau/Open-Measurement-JSClients)).
Session ownership under JavaScriptSessionService is **documented**: the WebView is "responsible
for starting/finishing ad sessions via the JS Session Client"; native provides "native-layer
measurement signals". With `isHTMLAdView:true`, "all ad sessions will be of type 'html' and
calling `setAdView` is not required" (iOS class reference, URL above).

**Verdict Q1: in-app, the WebView runs the NATIVE SDK's service script (`omsdk-v1.js`),
provided/injected by the host integration — SHARC must NOT boot `omweb-v1.js`, and the two do
not coexist.** Coexistence is **inferred**-forbidden, not documented-forbidden: both builds
install the OMID JS Service surface at the same well-known detection point (the service
"provides a detection mechanism which the OMID JS client will use" — v1.5 p.13; one detection
point, two claimants = undefined behavior), and even a hypothetical clean namespace split would
leave two measurement authorities answering one session — exactly the split-authority failure
class D5/#378 isolation work exists to prevent. We treat coexistence as a misconfiguration, not
an option.

### 1.2 The mode switch: `serviceMode` (operator-declared, strictly validated)

`OmidCompatBridge` gains a constructor option:

```js
new OmidCompatBridge({
  serviceMode: 'native',                     // 'web' (default) | 'native'
  omSdkSessionClientUrl: '.../omid-session-client-v1.js',
  // omSdkServiceScriptUrl MUST be absent in 'native' mode — see failure modes
  partnerName: ..., partnerVersion: ...,
})
```

- **`'web'` (default)** — today's behavior, byte-identical: `_ensureSdkLoaded()` injects
  `omSdkServiceScriptUrl` (omweb-v1) then `omSdkSessionClientUrl`; feature advertised only when
  both URLs are configured (`_hasSdkInjectionUrls`).
- **`'native'`** — `_ensureSdkLoaded()` NEVER injects a service script. It injects only the
  session client, then waits (bounded, the existing 5s script-timeout figure) for the
  native-provided service to be reachable via the session client's public
  `AdSession.isSupported()` probe — true iff the client's communication resolved against a
  service or the native `omidSessionInterface` exists, covering both native injection shapes
  *(corrected 2026-07-10, #433 review — the session client exports its namespace
  unconditionally at script-evaluation time, so namespace presence proves only that the
  client script ran; service presence is only observable via `AdSession.isSupported()`)*.
  Feature advertisement requires only `omSdkSessionClientUrl`.

**Why operator-declared, not detected:** platform sniffing (`webkit.messageHandlers` /
`window.omidNative` probes) is undocumented, platform-specific, and a misdetection silently
forks measurement authority — the one failure this switch exists to prevent. The operator
embedding the container in an app *knows* it did so; declaring it is one constructor field.
This mirrors the NHI posture (S1: host capabilities are declared, never inferred from presence).

**Validation (Rule-11/13 house pattern — construction-time enum, strict):**
- `serviceMode` must be `undefined`, `'web'`, or `'native'` → anything else throws `TypeError`
  at construction. No coercion, no silent default-on-garbage.
- `serviceMode:'native'` **combined with** `omSdkServiceScriptUrl` throws `TypeError` at
  construction — a contradictory authority declaration ("native provides the service" + "here is
  a service to inject") is a config bug, and injecting omweb next to omsdk-v1 is the harmful act
  itself. Fail loud before any script moves.

**Failure modes when misconfigured:**
- `'native'` declared, no native service actually present (host forgot to inject omsdk-v1):
  the bounded wait elapses → `feature_load_failed` on the structured channel with new reason
  `native-service-missing` (joins the existing `_classifySdkLoadError` vocabulary). The ad still
  renders; measurement honestly fails; validator buckets it vendor/operator-attributable — the
  container answering honestly, per G5's attribution discipline.
- `'web'` left defaulted inside a WebView where the host injected omsdk-v1: `_ensureSdkLoaded`'s
  existing service-already-present idempotence check ("a publisher may already have loaded the
  OM SDK service") means the bridge does NOT stack a second service; behavior degrades to the
  native service being the authority with SHARC unaware of the mode. Additionally the bridge
  emits a one-time `console.warn` when a service is detected pre-injection while
  `serviceMode:'web'` — a dev-channel nudge toward the explicit declaration. (The structured
  channel stays quiet: measurement works in this configuration; warning ≠ failure.)

### 1.3 What does NOT change

Hop-1 is untouched: the creative-iframe `omid3p` shim, the `SHARC:Omid:` router protocol, nonce
trusted-injection (§4.3), phase gating (`omid-active`/`omid-finishing`), verification-resource
cap, and the G5 T2 nonce-over-port seam all ship byte-identical in-app. `OmidCompatBridge`
retains AdSession ownership (start/finish via the session client) in both modes — that is the
documented JavaScriptSessionService division of labor, and it is why hop-2 is wiring.

## Decision 2 — Single geometry authority

### 2.1 The problem, stated honestly

In-app, the OM SDK computes its own geometry: the native layer registers the WebView as the ad
view ("Set the view on which to track viewability. For a WebView ad, this will be the WebView
itself" — Android guide §set-session-view) and geometry events carry native measurement.
**Documented** (OMID API v1.5, geometryChange event data, pp.45–48): "In the case that no
creative element at the web-layer level exists or is available to measure, this will measure the
geometry of the native-layer WebView container" — with `containerGeometry` /
`onScreenContainerGeometry` carrying the native WebView rect when both layers measure. SHARC
cannot substitute its composed effective-visibility as the OM SDK's geometry feed; that emission
path belongs to omsdk-v1 + native signals.

Meanwhile SHARC's ratified invariant is **wire == MRAID == SafeFrame == OMID**, all fed from the
ONE composer (Slice C/D). As literally stated, the invariant cannot bind the native OM SDK's own
geometry stream — we do not own it.

### 2.2 The ruling: one physical source, two measurement paths, agreement asserted

**The single authority in-app is the WebView's on-screen geometry as measured by the host — fed
to BOTH consumers from that one physical source:**

1. **Host → SHARC composer:** the host derives an on-screen exposure percent for the WebView and
   pushes it via the existing `setHostExposure(pct)` INPUT (axis-3, host-wins — NHI roster row,
   Slice C reconciliation note). Everything SHARC emits — the wire's
   `effectiveVisibilityChange`, MRAID `exposureChange`/`viewableChange`, SafeFrame geometry,
   and the OMID **relay** (`_signalVisibilityFromEffective` → the iframe shim's geometryChange)
   — continues to read the ONE composer. The invariant holds unmodified for every
   SHARC-emitted surface, in-app exactly as on web.
2. **Host → OM SDK native:** the same WebView is what native registers with the OM SDK
   (JavaScriptSessionService created with the WebView; `isHtmlAdView:true` makes the WebView
   frame the ad view). The OM SDK measures that same rect through its own pipeline.

**Restated invariant (L1-spec language for the G1 slot):**
> In-app, `wire == MRAID == SafeFrame == OMID-relay` continues to hold by construction (one
> composer). The OM SDK's native geometry stream is an *independent measurement of the same
> WebView frame*, not a SHARC emission; conformance therefore additionally requires
> **agreement**: at visibility steady state, the composer's `effectivePercent` and the OM SDK's
> `percentageInView` for the registered WebView MUST agree within rounding tolerance.

**Conformance check (the G6 harness gate):** a fixture creative with a verification-client
subscriber captures native `geometryChange.percentageInView` while the harness captures the
composer's `effectivePercent`, at three driven plateaus — fully visible (100), partially
occluded/offscreen (~50), and app-backgrounded (0, reason `backgrounded`). *(Amended
2026-07-10 per #433 internal review, CR-F5: the EV reason `'frozen'` is STRUCTURALLY
unreachable in-app — it is driven by the composer's axis-2 freeze sub-state, which only the
page-lifecycle `freeze` event sets, and per the ratified split the host-lifecycle INPUT never
touches the composer. `'backgrounded'` is the honest in-app vocabulary; a harness plateau
must assert `backgrounded`, never `frozen`.)* PASS =
|composer − native| ≤ 1 at each plateau AND the visible/notVisible boolean flips agree in both
directions. This is the "harness asserts agreement" resolution the discovery ruling anticipated,
and it is a real check: it catches a host that feeds `setHostExposure` from anything other than
the WebView's actual on-screen rect (S2 discipline — offset is never visibility; exposure must
be the real on-screen percent).

Why not "native wins, composer defers"? Because the composer feeds MRAID/SafeFrame/wire, which
must work with OMID absent (unmeasured inventory), and because axis-2 (parentVisible /
host-lifecycle, Decision 4) is SHARC-owned by design — a reparented full-screen WebView on a
backgrounded host is still 0% effective (NHI S2 carry-forward). Why not "composer wins, suppress
native geometry"? We cannot — and should not — intercept the OM SDK's own service-to-verifier
stream; vendors trust it precisely because the measurer isn't the measured.

## Decision 3 — Finish-before-teardown (in-app teardown sequence)

**Documented** (OMID API v1.5, p.16; identical language in both platform guides):
> "So that the verification scripts have enough time to handle the 'sessionFinish' event, the
> integration must maintain a strong reference to the WebView for at least 1.0 seconds after
> ending the session."

SHARC's container-side ordering is already pinned by `test:terminate-omid-order`: `_terminate()`
relays the terminal `sessionFinish` while the router is in `omid-finishing`, BEFORE
`transitionTo('terminated')` + destroy; the grace window is **SHARC's chosen ~1.5s** (0.7.8
Risk R1 — the OMID spec leaves the exact figure to the player). Nothing about that ordering
changes in-app. What is NEW in-app is that a party outside the page — the host app — can destroy
the JS realm itself. Hence a normative host requirement.

**The in-app teardown sequence (normative, L1-spec prose for the G1 slot):**

1. The host initiates dismissal by asking the *container* to close (invoke `destroy()` /
   `close()` on the container via the host page — never by deallocating the WebView first).
2. The container's `_terminate()` runs unchanged: sessionFinish relayed in `omid-finishing`,
   router then terminated (pinned ordering).
3. **HOST-REQ-1 (normative):** the host app MUST hold a strong reference to the
   WKWebView / Android WebView — and MUST NOT suspend, navigate, or deallocate it — for at
   least **1.0 s** after session finish (OM SDK minimum, documented above). SHARC RECOMMENDS
   **1.5 s** to cover the container's own `omid-finishing` grace with a single figure. Only
   then may the host remove the WebView from the hierarchy and release it. On iOS this also
   means dismissal-driven teardown must not ride `deinit` ordering; schedule the release.
4. If the host uses the native `JavaScriptSessionService` teardown API, note its documented
   semantics: teardown "finishing all currently active ad sessions measured by this service
   instance" may itself "require up to one second" — call it only AFTER step 2's JS-side finish
   has run, or accept that native force-finishes the session out from under the bridge (the
   bridge's `sessionFinished` latch makes this safe but the verdict becomes native-attributed
   timing, not SHARC's pinned ordering).
5. Crash-path exception: `webViewWebContentProcessDidTerminate` (iOS,
   [Apple reference](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webviewwebcontentprocessdidterminate(_:)),
   documented-cited) / `onRenderProcessGone` (Android) means the JS realm is already gone — the
   grace is forfeit by construction, no sessionFinish can be delivered, and the host's only
   duties are disposal and (harness context) reporting the run as infrastructure-failed. See
   Decision 4.4 seam U5 for why this is NOT an INPUT value.

**Who holds the WebView: the host app, per the NHI contract.** HOST-REQ-1 enters the NHI ADR as
a host-obligation clause when the amendment lands (Decision 5) — it is the first NHI member
that constrains the *host's* lifecycle behavior rather than a container API shape, which is why
it is spelled as normative prose, not a method.

## Decision 4 — Lifecycle-mapping study + the host-lifecycle INPUT

### 4.1 Primary-source basis

- **iOS view layer** — `viewDidAppear(_:)` / `viewWillDisappear(_:)`
  ([Apple UIViewController reference](https://developer.apple.com/documentation/uikit/uiviewcontroller/viewdidappear(_:)),
  documented-cited): view-controller visibility within the app, fires for in-app navigation
  as well as app-level transitions.
- **iOS scene/app layer** — `UIScene.ActivationState`
  (`foregroundActive` / `foregroundInactive` / `background` / `unattached`;
  [Apple reference](https://developer.apple.com/documentation/uikit/uiscene/activationstate-swift.enum),
  documented-cited) and the classic `UIApplication.State` triple. `foregroundInactive` =
  visible but not receiving events (app switcher, system alert, control center).
- **Android activity layer** — `onStart`/`onResume`/`onPause`/`onStop`
  ([Activity lifecycle guide](https://developer.android.com/guide/components/activities/activity-lifecycle),
  documented-cited): RESUMED = foreground+interactive; STARTED-not-RESUMED = visible,
  not foreground; STOPPED = not visible.
- **Android multi-window** — **documented** (verbatim-verified,
  [multi-window guide](https://developer.android.com/guide/topics/large-screens/multi-window-support)):
  Android 10+: "All activities remain in the RESUMED state when the device is in multi-window
  mode." Android 9−: "only the activity the user has most recently interacted with is active at
  a given time… All other visible activities are STARTED but are not RESUMED." And the playback
  guidance: video apps should "begin playback in response to ON_START, and pause playback in
  response to ON_STOP" — i.e., visibility, not focus, is the platform's own recommended axis
  for content that should keep running.
- **Android process layer** — `ProcessLifecycleOwner`
  ([AndroidX reference](https://developer.android.com/reference/androidx/lifecycle/ProcessLifecycleOwner),
  documented-cited): whole-process ON_START/ON_STOP (ON_STOP dispatched after a delay past the
  last activity's stop, absorbing configuration-change flicker; ON_DESTROY is never dispatched).
- **Web page-lifecycle** — W3C Page Visibility (visible/hidden) and **documented**
  (verbatim-verified, [WICG Page Lifecycle](https://wicg.github.io/page-lifecycle/)): frozen =
  "the document is frozen, any tasks associated with the document will not run"; `freeze`/
  `resume` events; discarded via `document.wasDiscarded`.
- **Engine reality check (inferred from implementation status, load-bearing):** WebKit does not
  implement the WICG `freeze`/`resume` events, and inside an app WebView there is no
  browser-chrome actor to fire them regardless. The HtmlAdapter's FROZEN wires
  (`freeze`/`pagehide{persisted}`) therefore never fire in-app. **The host INPUT below is the
  ONLY source of FROZEN in-app.** This single fact is why the INPUT is a formal L1 surface and
  not a convenience.

### 4.2 The mapping table

Severity order (for the precedence rule in 4.3): `active < passive < hidden < frozen`.

| # | Native callback / state | Page-lifecycle analog | SHARC container state | Basis |
|---|---|---|---|---|
| M1 | iOS `viewDidAppear` + scene `foregroundActive` / Android activity RESUMED | active | **ACTIVE** | clean |
| M2 | iOS scene `foregroundInactive` (app switcher, system alert) / Android STARTED-not-RESUMED (API ≤28 multi-window unfocused, dialog over activity) | passive (visible, not focused) | **PASSIVE** | clean |
| M3 | iOS `viewWillDisappear` (VC covered/popped, app still foreground) / Android activity STOPPED while process still STARTED (another in-app activity on top) | hidden | **HIDDEN** | clean |
| M4 | iOS scene `background` (`sceneDidEnterBackground` / `applicationDidEnterBackground`) / Android `ProcessLifecycleOwner` ON_STOP (whole app backgrounded) | hidden → frozen | **FROZEN** | ruling U1 |
| M5 | iOS foreground return (`sceneWillEnterForeground`→`foregroundActive`) / Android process ON_START + activity RESUMED | resume → active/passive | **FROZEN-exit via adapter resolution** (existing `_resolveRestoreDestination` machinery) | clean |
| M6 | Android 10+ multi-window: RESUMED but `onTopResumedActivityChanged(false)` | visible + unfocused | **ACTIVE** (focus ignored) | ruling U2 |
| M7 | iOS/Android process death while backgrounded (jetsam / LMK) | discarded | **unrepresentable — no transition is delivered; cold start on return** | ruling U4 |
| M8 | `webViewWebContentProcessDidTerminate` / `onRenderProcessGone` (app alive, WebView engine process died) | terminated (realm gone) | **host-side disposal, NOT an INPUT value** | ruling U5 |

### 4.3 The two-axis precedence rule (design core)

The clean pattern that falls out of both platforms: **view-layer signals are a visibility axis;
app/process-layer signals are a freeze axis.** The adapter never lets the page's own (in-app:
mostly blind) signals *out-promote* the host's assertion:

> `SHARC state = most-severe( host-asserted state, page-derived state )` on
> `active < passive < hidden < frozen`.

This mirrors the composer's axis gate (effective = parentVisible ? intersection : 0) and OMID's
own multi-axis reduction. In-app the host page is 1:1 with the WebView, so in-page
IntersectionObserver reads ~100% permanently — real exposure arrives via `setHostExposure`
(axis-3) and real state via this INPUT; the in-page signals remain as a defensive floor, not the
authority.

### 4.4 Unclean seams — explicit rulings

- **U1 — iOS `viewWillDisappear` vs scene `background` (the double-fire).** Backgrounding an
  app fires view-level disappearance AND scene background; in-app navigation fires only the
  former. Ruling: the view axis maps to HIDDEN (M3), the scene/process axis maps to FROZEN
  (M4), and the most-severe rule resolves the overlap — backgrounding lands FROZEN regardless
  of callback arrival order; in-app navigation lands HIDDEN and never FROZEN. Rationale: after
  `viewWillDisappear` alone, JS still runs (timers fire, ports deliver) — that is HIDDEN's
  contract, not FROZEN's. FROZEN is reserved for "tasks will not run" (WICG definition), which
  on iOS is what backgrounding leads to (suspension follows `didEnterBackground` at the
  system's discretion, with no further callback — the pessimistic immediate FROZEN at
  background-entry is deliberate: it is the last moment we are guaranteed to be told).
- **U2 — Android multi-window resumed-but-not-focused.** Ruling: map by visibility, ignore
  `onTopResumedActivityChanged` for state (M6 → ACTIVE). Rationale: the platform's own guidance
  says content that should keep running keys off ON_START/ON_STOP, not focus; an ad in a
  visible-but-unfocused window is on screen and measurable, and OMID's `noWindowFocus` is an
  adjustment *reason*, not a visibility kill. Focus loss that ALSO reduces interactivity on
  API ≤28 arrives as STARTED-not-RESUMED and correctly lands PASSIVE via M2 — no special case
  needed.
- **U3 — Android `onPause` ambiguity (visible-paused vs about-to-stop).** `onPause` alone
  cannot distinguish "dialog over me" from "first step of vanishing." Ruling: map `onPause` →
  PASSIVE and let `onStop` (→ HIDDEN/FROZEN per M3/M4) arrive if vanishing continues — the
  transient PASSIVE between them is truthful ("visible, not foreground") and costs one deduped
  transition. Never map `onPause` directly to HIDDEN: on API ≤28 multi-window, a paused
  activity can stay fully visible indefinitely.
- **U4 — process death vs FROZEN.** Backgrounded-app kill delivers no callback on either
  platform; there is nothing to map and no port to deliver it on. Ruling: FROZEN is the
  terminal *deliverable* background state; process death is documented as unrepresentable
  (parallel to web bfcache eviction, where the next signal is a cold load). The harness treats
  a killed-and-relaunched run as a fresh container, never a restore. No `wasDiscarded` analog
  is invented.
- **U5 — WebView engine-process death while the app lives (M8).** The container's realm is
  gone; ANY enum value for this would be undeliverable by construction (the setter would be
  invoking JS in a dead WebView). Ruling: NOT an INPUT value. It is a host-side disposal event:
  the host discards the page (and in harness context reports the row as
  infrastructure-failed / `sharc-runner-error` attribution), then recreates if desired. The
  DoD's `terminated`-mapping language for process kill is satisfied by *host bookkeeping*, not
  by a wire delivery — stating this explicitly prevents a future "why doesn't the adapter
  handle onRenderProcessGone" round-trip.
- **U6 — delivery-before-suspension (iOS).** `evaluateJavaScript` from `didEnterBackground` is
  asynchronous and may not complete before suspension. Ruling: the INPUT is best-effort at
  freeze-entry, and the host MUST re-assert the current state on every foreground return
  (host-side replay; the container-side dedup makes re-assertion idempotent). This is the C7
  replay discipline read from the host's side, and it is why dedup semantics are part of the
  INPUT contract rather than an optimization.
- **U7 — host-axis RISE triggers a recompute of the most-severe function** *(added 2026-07-12
  per #438 — simulator-observed gap: the ceiling was demote-only)*. A host assertion MORE
  permissive than the previous one (e.g. the M5 foreground return's `frozen → passive →
  active` tail) re-evaluates `most-severe(host, page)` and PROMOTES the container to the
  composed target through the pre-clamped promotion chokepoint. Rationale: 4.3's rule is a
  function of both axes in BOTH directions, but the demote-only cap plus in-app page-axis
  blindness (4.1 — WKWebView fires no freeze/resume and no visibility/intersection edge on a
  background → foreground round-trip) left the rise direction with no recompute trigger at
  all: the real-device round-trip stranded the container at PASSIVE
  (`["ready","active","passive","hidden","frozen","passive"]`, #438) with the U6 re-asserts
  deduping to no-ops. Constraints: a page-held freeze still holds FROZEN (per-axis latches,
  most-severe); a pre-ready container never jumps (the recompute acts only ON the visibility
  axis — the handshake race rules own LOADING/READY); and when the page axis has NEVER
  asserted (no IO sample yet), it contributes `'active'` — a non-asserting page axis does not
  constrain, so the host assertion governs alone (failing closed would re-create the strand).
  U6 re-asserts after the rise remain free under the dedup.
  **Security boundary (SE review, #441):** host-rise moves only the container
  ENUM, never a measurement value — the OMID impression is one-shot
  (`impressionFired` latch: a re-promotion after a demote cannot re-fire it),
  and viewability (`percentageInView`, MRAID `viewableChange`) is sourced from
  the composed effective-visibility axis (`setHostExposure`/the composer), not
  the enum. So host-rise adds NO inflation power beyond `setHostExposure`; a
  host that asserts lifecycle `'active'` while backgrounded without the dual
  `setHostExposure(0)` (U7/§4.6) is a dual-assert-contract violator — the same
  trusted-host boundary that already governs the exposure axis, unchanged here.

### 4.5 The L1 INPUT shape — NHI ADR AMENDMENT (to be applied to `2026-07-03-l1-native-host-integration-surface.md` at develop time)

> **AMENDMENT (proposed here, applied to the NHI ADR when the implementation lands):** add one
> INPUT member to the roster, and one host-obligation clause (HOST-REQ-1, Decision 3).

- **Member:** host-lifecycle — **`setHostLifecycle(state)`** (C6 naming: host→container INPUT
  setter, `set*`).
- **Direction:** HOST-PROVIDED INPUT (host → container → named runtime consumer).
- **Enum:** `'active' | 'passive' | 'hidden' | 'frozen'` — deliberately the page-lifecycle
  vocabulary, not the platform vocabularies, so one enum serves both platforms and the web
  semantics stay the reference. No `'terminated'` (U5); no `null`-to-clear (a lifecycle always
  has a value; clearing would mean "host stops knowing," which is not a state — the host simply
  stops calling and the last assertion stands under the most-severe rule).
- **Declared consumer:** the **app lifecycle adapter** (`AppLifecycleAdapter`,
  `src/lifecycle-adapters/app-adapter.js`) — NEVER the bridge (C2; exposure feeds the composer,
  lifecycle feeds the adapter, nothing host-provided ever touches a compat bridge directly).
  Plumbing mirrors `setHostExposure`: the container stores `_hostLifecycle` and invites the
  adapter (`_onHostLifecycle` hook, base-class no-op) to re-derive; the adapter applies the
  most-severe rule of 4.3 using its existing transition helpers (`_transitionToFrozen`,
  `_resolveRestoreDestination`).
- **Validation (validate-first, strict — Rule-11/13 pattern):** a value outside the enum throws
  `TypeError`. Deliberate divergence from `setHostExposure`'s silent-ignore: a jittery numeric
  stream tolerates sample-dropping; a lifecycle enum from adapter glue is programmer error, and
  a silently dropped `'frozen'` leaves the container measuring a suspended app — the worst
  silent failure this surface can produce. Enum inputs fail loud (the `forceOrientation:
  'banana'` lesson, C5, escalated to throw because the caller is the host integration, not the
  creative).
- **Dedup:** consecutive-identical values are no-ops (mirrors `_lastSentState` / composer dedup)
  — required so U6's mandatory host re-assertion is free.
- **Replay (C7):** last-value-latched — a value asserted before the adapter attaches (preload)
  is retained and applied at attach; on each ACTIVE transition the adapter re-evaluates against
  the latched host value exactly as `_syncAudioState` re-delivers. Host-side complement: U6's
  re-assert-on-foreground requirement.
- **Web inertness (C1/C3):** ships in the bundle; no host wired ⇒ never called ⇒ zero behavior
  change; stock web embeds byte-identical. Conformance test per member (C8) and G6 gate
  membership (C9) as per the profile.
- **Adapter selection:** container constructor option `hostContext: 'web' | 'app'`
  (default `'web'`, Rule-11-strict — non-enum throws `TypeError`);
  `_selectLifecycleAdapter(apiFramework, hostContext)` returns `AppLifecycleAdapter` for
  `'app'`. `AppLifecycleAdapter extends HtmlAdapter` — it *layers* the host axis on the
  browser-native signals exactly as the adapter family header always promised framework
  subclasses would ("layer framework-specific signals on top", base-adapter.js). Operator-
  declared for the same reason as `serviceMode`: the embedder knows; sniffing lies.

### 4.6 Host-integration MUST — the backgrounding DUAL ASSERT (SE-F3) *(amended 2026-07-10 per #433 internal review)*

**Normative (L1-spec prose for the G1 slot — seam-census material):** when the app
backgrounds (M4) or the container's view is covered/off-screen (M3), the host integration
MUST assert BOTH inputs:

> `setHostLifecycle('hidden')` **AND** `setHostExposure(0)`

The two surfaces feed deliberately disjoint consumers (NHI C2, the ratified
lifecycle-never-touches-composer split): **lifecycle feeds state** (the adapter's two-axis
most-severe rule → container state, MRAID `stateChange`, OMID session gating), while
**exposure feeds measured visibility** (the effective-visibility composer → the wire's
`effectiveVisibilityChange`, MRAID `exposureChange`/`viewableChange`, SafeFrame geometry, the
OMID relay). A host that asserts only the lifecycle leaves the composer reporting the last
on-screen exposure percent for a hidden container — measurement lies while state tells the
truth; a host that asserts only the exposure leaves the container's state axis believing the
page is interactive. Neither input derives the other by design. The symmetric foreground
return re-asserts both (`setHostLifecycle(<current>)` per seam U6's mandatory replay +
`setHostExposure(<current pct>)`). This clause joins HOST-REQ-1 in the NHI ADR's
host-obligation set when the amendment lands (Decision 5), and the G6 harness gate asserts
both surfaces at the backgrounded plateau.

## Decision 6 — iOS harness-skeleton spike CONTRACT (design only; no Xcode work in this pass)

**What the walking skeleton must demonstrate, end to end:**

1. **Serve:** a local HTTP server (the existing `server.cjs` two-origin harness pattern; ATS
   exception for localhost in the app's Info.plist) serves the host page + `dist/` bundles +
   the G5 fixture pages, host and creative on distinct origins/ports (cross-origin mandatory,
   per G5's serving-topology ruling).
2. **Boot:** a minimal Swift app creates one `WKWebView`, loads the host page over local HTTP;
   the page constructs `SHARCContainer` (with `hostContext:'app'` once it exists; skeleton may
   run pre-INPUT with the HtmlAdapter — the spike proves plumbing, not the adapter) and boots
   the G5 fixture suite via an in-page runner.
3. **Egress:** results leave the page via
   `window.webkit.messageHandlers.sharcHarness.postMessage(row)` — one message per fixture row
   plus a terminal `{type:'summary'}` message. **Row schema is EXACTLY what the fail-closed
   compare tool consumes** (`tools/creative-validator/src/regression.js`): identity fields read
   by `reportKey` — `case.source.sourceFile`, `case.source.rowIndex`, `case.source.bidder`,
   `case.source.mtype`, `case.ids.bidId`, `case.ids.crid` — and verdict fields read by
   `verdict` — `outcome.status`, `outcome.bucket`, `outcome.reason`. The native side does ZERO
   interpretation: it serializes each row as one NDJSON line.
4. **Surface:** the app prints NDJSON to stdout; the runner script launches via
   `xcrun simctl launch --console` (or boots + tails), collects rows into a report file, feeds
   it to `compareReportVerdicts` against the same-fixture web baseline, and exits nonzero
   unless `regressionClean` and row-count parity hold. Success/failure reaches CI as an exit
   code, identical in spirit to every existing validator gate.
5. **Proves for G6 sequencing:** local-HTTP serving works under ATS; the container boots
   unmodified in WKWebView; the messageHandlers egress carries the compare-tool schema; and the
   compare tool accepts an in-app-produced report with zero format shims. Lifecycle, OMID, and
   the exfiltration must-test then land on this skeleton rather than inventing transport later.

**Tooling decision — self-running app + stdout over XCUITest.** Recommendation: self-running.
Rationale (one line): the verdicts already egress as data rows, so XCUITest would add a
UI-automation layer that asserts nothing the NDJSON stream doesn't already carry — the runner
script + compare tool ARE the test framework. (Named residual: XCUITest becomes worth it the
day a case requires synthesized user gestures; the expand/collapse round-trip does not — the
fixture drives it from JS.)

## Consequences

**Easier:** in-app OMID reduces to one constructor enum + one absent injection; the invariant
survives with a sharper statement (SHARC-emitted surfaces identical by construction, native
agreement asserted); the lifecycle INPUT reuses every existing adapter helper and the
setHostExposure plumbing pattern; the harness inherits the G5 fixture suite and the regression
tool unchanged.

**Harder / accepted:** the geometry invariant is now two-clause (construction + asserted
agreement) rather than one — honest, since we don't own the OM SDK's stream; `serviceMode` and
`hostContext` grow the constructor surfaces (both Rule-11-strict, both inert-by-default);
FROZEN in-app depends entirely on host discipline (U6 re-assertion), which the conformance
docs must state loudly; Apple/Android reference pages resisted verbatim extraction this pass
(JS-rendered) — their rows are marked documented-cited, and the multi-window + WICG + OMID
claims that carry the actual rulings ARE verbatim-verified.

**Rollback:** fully additive — `serviceMode`/`hostContext` default to today's behavior;
`setHostLifecycle` unwired is dead weight only; `test:g6-red` is not in any gate.

*Out of scope (stated, not designed):* Android harness specifics beyond parity with the iOS
contract (same egress schema via `addJavascriptInterface`), productized SDK integrations
(post-1.0, vendors are this channel's Prebid), CTV/DOOH adapters, any native container code.
