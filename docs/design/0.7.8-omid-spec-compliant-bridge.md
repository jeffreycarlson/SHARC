## 0. What changed from the parked draft

This revision rebases the parked pre-router draft (commit `6bbe69b`) onto the shipped 0.7.7 router. A reviewer who knows the parked draft should read this section first.

> **Revision pass — review-driven (this commit).** Three fresh-context reviews (Architecture, Security, IAB-spec-compliance) ran on the prior router-consuming draft (`c88dc31`); Jeffrey locked the open questions. This pass folds those decisions in:
> 1. **Replay is full, literal, and spec-baseline — the replay path is never capped or coalesced.** The prior draft narrowed late-registrant replay to the most-recent `sessionStart` (cap 1) and labeled replay "beyond the OMID spec's letter." Both were wrong. Late-registrant catch-up is **mandated** by the OMID Web Implementation Guide v1.0 ("Event Caching" p.13; "Ad Session Lifecycle" step 8). SHARC now replays **all** previously-fired events of the subscribed type, in chronological order, with **no replay-time cap and no replay-time coalescing** (§ 5.4, OMID-D14, OMID-Q5). Amplification is bounded at the two **inputs** to replay — observer count and cached-log size — never on the replay path itself (§ 7.3).
> 2. **`Register` phase gate narrowed to `omid-active` only.** The shim defers posting `SHARC:Omid:Register` to the publisher until `sessionStart`, so the inbound envelope can only legitimately arrive in `omid-active`. This also closes a first-impression race against the async nonce gate (§ 3.2, OMID-Q1).
> 3. **URL/`srcdoc` nonce injection committed to MessageChannel.** No longer an implementation spike: the container posts a `MessageChannel` port into the `srcdoc` frame at creation; the shim's port-receive handler stashes the nonce as a closure constant before any creative code runs (§ 4.3, OMID-Q4 → resolved, OMID-D2).
> 4. **OMID phase transitions: resolution (b) is REQUIRED, not preferred.** Router § 9.6 test #1 requires every declared phase to have a `transitionTo` site in `sharc-container.js`; an extension-exposed `transitionTo` (resolution a) would place the site in the extension and fail that test. (a) is foreclosed (§ 3.4, OMID-Q2, OMID-D19).
> 5. **Amplification is bounded at BOTH inputs to replay, not at the replay.** Replay's cost is `O(observers × cached_events)`; both factors are bounded at their *inputs*, neither of which is the replay path. **Observers** → the cumulative-register-calls/session subscription cap (single honest unit — no vendor unregister surface exists, so live count equals the cumulative count), value owned by #244. **Cached-log size** → bounded at *emission* (`geometryChange` rate-limit as a player-cadence sampling choice; an emission-side cap on distinct cached `sessionError`s; session-singletons already ≤1). The cap is **not** "the single load-bearing guard" — it bounds only the observer factor (§ 7.3, OMID-D6). The cap **value** is provisional, owned by #244 (validator measures the observer-count distribution; value set at p99 + headroom); the provisional default ships finite and conservative, never unbounded. Do not read 64 as final (§ 7.3, OMID-D6).
> 6. **Grace-window figure is SHARC's chosen value (~1.5s), not an OMID figure** — the spec says "on the order of seconds, exact value left to the player" (§ 3.4, Risk R1).
> 7. **Cached-log amplification axis RESOLVED (this commit).** Settled per owner decision: replay stays full and literal (no replay-time coalescing/capping — same category as the cap-1 narrowing already reversed); amplification is bounded at the two inputs (observer cap + emission-side event-rate bounds); the residual per-session replay cost (growing with session duration) is the **deliberate, accepted price of spec-faithful full replay**, kept tolerable by the input bounds and revisited only if #244 corpus data shows it is pathological (§ 5.4, § 7.3, § 13, § 14).

## 1. Problem Statement

0.7.3 locked OMID as a **container-only** measurement extension (D7 / D17): no creative-side API, no `window.omid3p` in the creative iframe. That decision matched the OM SDK Service Script / Session Client roles correctly for the **publisher-page side** of the integration but assumed the creative iframe would never host an OMID-aware verification script.

Three empirically-verified observations invalidate that assumption (see issue #217 evidence trail; corpus: 1,745 bids / 15 raw OpenRTB files, 422 declare AdCOM API 7):

1. **SHARC's current `OmidCompatBridge` exposes no `window.omid3p` anywhere.** `grep -rn "omid3p" src/` returns zero results in the production tree. `injectScripts(html)` and `injectIntoMarkup(html)` are explicit no-ops.

2. **The IAB OMID JS Verification Client expects `window.omid3p` in the same frame as the verification script.** The canonical detection code (`getThirdPartyOmid()` in IAB `Open-Measurement-JSClients` at `src/verification-client/verification-client.js`) reads `omidGlobal['omid3p']` from the resolved global context — it does **not** walk the frame tree, does **not** look at `window.parent` or `window.top`, and accepts only an object exposing two functions: `registerSessionObserver` and `addEventListener`. Verification scripts loaded inline in the creative iframe see no `omid3p` under SHARC today and fall back to non-OMID measurement modes.

3. **The corpus shows ~24% of API-7-declared bids (101 of 422) ship OMID-aware verification vendor scripts inline in the `adm`.** DoubleVerify's `cdn.doubleverify.com/dvtp_src.js` probes `t.omid3p` for `registerSessionObserver` capability, looks for `omweb-v1.js` in DOM, and accesses `omidVerificationProperties` — the canonical OMID JS Verification Client detection pattern. (For contrast: **0** corpus bids ship structured `verificationScripts` in `bid.ext.measurement.omid`, and **0** ship the canonical OMID Session Client in markup. The inline-`adm` path is the real-world OMID delivery channel.)

Separately, `OmidCompatBridge.options.verificationScripts` is a SHARC-invented config-time injection convention with **no IAB AdCOM/OpenRTB precedent for Banner or Video** (the AdCOM `OpenRTB support for OMSDK` doc defines a sidecar verification-script path only for Native, via `eventtrackers` with `event=555`). The path is still useful — publishers and wrappers do want to inject vendor scripts a creative did not bring inline — but it was positioned as the **canonical** delivery channel for HTML, and that framing is wrong.

**Scope of this design:** redesign the bridge to align with the IAB spec model — inline-loaded verification scripts find `window.omid3p` in the creative frame and register session observers — and express the publisher↔iframe event relay as a **router protocol** (prefix `SHARC:Omid:`), not bespoke machinery. `options.verificationScripts` is repositioned as supplementary (§ 8).

**SHARC-specific vs OMID-borrowed (acknowledgment, carried from router § 5.1).** The cross-frame back-channel between the publisher-page OMID extension and the creative-iframe shim is a **SHARC-specific** architectural feature. IAB OMID's canonical architecture has verification scripts running in container-loaded verification iframes with direct same-window `omid3p` access — no cross-frame channel, no nonce. The IAB OMID spec defines **no** nonce/token/signature/shared-secret mechanism; the AdSession identifier is a client-generated GUID and the trust model is structural same-realm co-location. SHARC needs a cross-frame transport that OMID's same-realm architecture never had, so SHARC's per-protocol nonce is solving a SHARC transport problem with standard crypto (the router's HMAC derivation), **not** implementing an IAB-spec requirement. This is engineering judgment, not a spec citation — and it must not leak into the IAB-facing `omid3p` surface (§ 9 dep 6).

The IAB three-role model is preserved exactly:
- **Container-side Service Script** (`omweb-v1.js`) ↔ **Session Client** (`omid-session-client-v1.js`) on the publisher page — the integration partner's per-measurement-context asset. SHARC is the integration partner.
- **Vendor Verification Client** inline in the creative iframe — probes `window.omid3p`.
- The **publisher-page-owned `AdSession`** is the single source of truth, emitting `loaded()` / `impressionOccurred()` / lifecycle. The iframe shim is a one-way relay of those events to inline verification scripts.

### 2.2 What is new in 0.7.8

1. **`src/sharc-omid-shim.js`** — a new iframe-side shim that installs `window.omid3p` with the IAB-spec surface (two methods, plus internal event delivery). Loaded into the creative iframe via the same install point as the MRAID and SafeFrame bridges (§ 4).
2. **`OmidCompatBridge` becomes a router consumer.** From its `onContainerLifecycleEvent(event)` hook (on `event.type === 'load'`), it calls `event.container.protocolRouter.register({ prefix: 'SHARC:Omid:', types, handler, onReady })`. It registers a session observer on its own `AdSession`, serializes events, and relays them across the publisher↔iframe boundary **through the router's outbound helper** to subscribers registered through the iframe shim.
3. **`options.verificationScripts` semantics narrowed** (documentation + framing only; same field name, same shape) — supplementary publisher/wrapper/vendor injection, not the canonical HTML OMID delivery channel (§ 8).

### 2.3 What is unchanged

- Publisher-page OM SDK loading (`omSdkServiceScriptUrl`, `omSdkSessionClientUrl`). 0.7.3 § 3 stands.
- Container-owned `AdSession.start() / loaded() / impressionOccurred() / finish()` lifecycle. 0.7.3 § 4 stands.
- Feature name `com.iabtechlab.sharc.omid` in `supportedFeatures` when both SDK URLs are configured. 0.7.3 § 7 stands. AdCOM **API framework code 7** anchoring (per `project_adcom_anchor`) is unchanged — `creativeMeta.apis` carries code 7 for OMID-capable creatives.
- `KNOWN_BRIDGE_IDENTIFIERS` is **NOT** extended to include `'omid'` (§ 4.2) — OMID still does not route through the renderer-bridge resolver as an API-translation bridge.
- 0.7.6 `omidAutoInstall` sidecar normalization. The bid-metadata path still produces `options.verificationScripts` entries; those become supplementary per § 8.
- The router itself. This design adds **zero router-side code** (router § 16.2: "zero router-side adjustments needed"). OMID is purely a consumer: it `register()`s a prefix; the **container** calls `transitionTo` at the right lifecycle points off a signal the OMID extension emits (OMID-Q2 resolution b — `transitionTo` stays container-internal per RTR-D14).

## 3. Transport: OMID as a router consumer

This is the load-bearing change from the parked draft. The IAB spec dictates the API surface inside the iframe (`window.omid3p` with `registerSessionObserver` / `addEventListener` — § 5). It does **not** prescribe how a publisher-page-owned `AdSession` reaches that surface when the verification script is inline in a cross-origin creative iframe. The parked draft answered that with bespoke postMessage gating; this revision answers it with the router.

### 3.1 OMID is the router's second occupant

OMID's publisher↔iframe transport is a stream of `window.message` envelopes under the `SHARC:Omid:` prefix. The router owns `window.message` (router § 2.5: it does **not** own `MessageChannel` ports). Because the OMID event relay is `window.message` traffic, it goes through the router's single `message` listener and uniform gate (router § 3.2). The OMID extension does **not** add its own `window.addEventListener('message', ...)`.

> **Why router `window.message`, not a dedicated `MessageChannel` (router § 16 dep 2 alternative).** Router § 16 dep 2 notes a `MessageChannel`-delivered OMID nonce "does not interact with the router at all." That is an option, but it would put OMID transport *outside* the router's discipline and reintroduce the bespoke-gating problem the router exists to eliminate. **Decision OMID-D1:** OMID transport rides the router's `window.message` channel under `SHARC:Omid:`, so the router gate validates every inbound OMID envelope. `MessageChannel` is reserved for one thing only — the one-time **trusted injection** of the OMID `protocolNonce` into the shim at iframe creation (§ 4.3), which is exactly the router-§16-dep-2 "MessageChannel-transferred at iframe creation" mechanism. Steady-state OMID events ride the router channel; only the initial secret hand-off uses the port. This keeps the gate authoritative for all ongoing traffic.

### 3.2 Registration shape

`OmidCompatBridge.onContainerLifecycleEvent(event)` fires on `event.type === 'load'` (after the renderer protocol is already registered by the container itself — router § 2.3 ordering). It calls:

```javascript
// In OmidCompatBridge, from onContainerLifecycleEvent({ type: 'load', container }):
container.protocolRouter.register({
  prefix: 'SHARC:Omid:',
  types: {
    // Inbound: iframe shim → publisher. Subscription handshake. The shim queues
    // registerSessionObserver/addEventListener calls locally pre-session and posts
    // SHARC:Omid:Register ONLY at sessionStart (when the container enters
    // omid-active), so a legitimate Register can never arrive before omid-active.
    'Register': { phases: ['omid-active'], direction: 'inbound' },
    // Outbound: publisher → iframe. Session lifecycle + metric events.
    // Session control (start/finish) valid across the OMID-active window.
    'Event':    { phases: ['omid-active', 'omid-finishing'], direction: 'outbound' },
  },
  handler: this._handleOmidEnvelope.bind(this),   // payload-shape + dispatch ONLY; gate already done
  onReady: ({ protocolNonce }) => {
    // Router-derived OMID per-protocol nonce. Stash for outbound construction
    // and for trusted injection into the shim (§ 4.3). Never echoed to vendor JS.
    this._omidProtocolNonce = protocolNonce;
  },
});
```

The router validates `(source, origin, prefix, type-membership, placementSessionId, OMID protocolNonce, phase-membership)` on every inbound `SHARC:Omid:Register` envelope before `_handleOmidEnvelope` ever runs (router § 3.2 steps 1–9). The handler is responsible **only** for payload-shape validation (`subscription.kind`, `injectionId` present, etc.) and dispatch into the subscription registry.

> **Resolved — OMID-Q1 (phase membership for `Register`): narrow to `omid-active` only.** Per OMID's "call upon initialization" semantics, a verification script may call `registerSessionObserver` *before* `AdSession.start()` (the script runs as soon as the creative HTML executes; the publisher-page session may still be loading). The shim **queues** such early calls locally (§ 5.5) and posts `SHARC:Omid:Register` to the publisher **only at `sessionStart`** — i.e. only once the container has entered `omid-active`. A legitimate `Register` envelope therefore can never arrive before `omid-active`, so the `types` map declares `Register` valid in `omid-active` only. This is the tightest correct gate, and it also closes a first-impression timing race: the OMID `protocolNonce` is delivered to the shim asynchronously (the router's `onReady` resolves after `crypto.subtle` derivation — router § 5.5). A `Register` posted at queue time, before that nonce has resolved on the shim side, would be silent-dropped at the router gate (no/wrong nonce). Deferring the post to `sessionStart` guarantees the OMID session — and therefore the nonce — has resolved before the shim ever signs an outbound envelope. The queue-vs-post timing (§ 5.5) and this phase gate are locked together.

### 3.3 Outbound envelopes go through `buildOutbound`

The publisher-side relay constructs `SHARC:Omid:Event` envelopes via the router helper (router § 3.3), which stamps the OMID `protocolNonce` and `placementSessionId` and asserts the type is declared `outbound`:

```javascript
const envelope = container.protocolRouter.buildOutbound('SHARC:Omid:', 'Event', {
  sequence: this._nextOmidSequence(),  // monotonic uint32, per session — OMID-payload field
  event: {
    adSessionId: this._adSessionId,    // OM SDK session id, read off the publisher AdSession
    timestamp: Date.now(),
    type: 'sessionStart',              // EventType per § 5.3
    data: { /* event-type-specific payload */ },
  },
});
// → { type: 'SHARC:Omid:Event', sharcNonce: <OMID protocolNonce>,
//     placementSessionId: <container.placementSessionId>, sequence, event }
this._container._iframe.contentWindow.postMessage(envelope, this._iframeOrigin);
```

`buildOutbound` throws synchronously if `sequence`/`event` collide with a router-controlled field (`type`/`sharcNonce`/`placementSessionId`) — they don't, so this is a programming-error tripwire, not a runtime concern (router § 3.3 / RTR-D2).

> **Note (division of labor).** `buildOutbound` only **stamps** the envelope (router-controlled fields `type`/`sharcNonce`/`placementSessionId`) and returns it. The actual `iframe.contentWindow.postMessage(envelope, this._iframeOrigin)` is the **bridge's** call, not `buildOutbound`'s — the router does not post outbound traffic (router § 2.5). The snippet above shows both steps; the second line is OMID's responsibility.

The iframe shim's **inbound** `SHARC:Omid:Register` envelopes are constructed the same way on the shim side, signed with the OMID `protocolNonce` the shim received via trusted injection (§ 4.3). The shim does not have access to `buildOutbound` (that's a publisher-page helper), so the shim constructs the envelope shape by hand but uses the injected nonce verbatim.

### 3.4 Phase transitions — the OMID lifecycle points

OMID declares its types against the router's **reserved** `omid-active` / `omid-finishing` phases (router § 4.1 — both reserved at RTR-J1 for exactly this consumer). No router code changes. The **container** (not the OMID extension) drives `transitionTo` at these points — the OMID extension emits a publisher-page session-lifecycle signal and the container maps it to the transition (OMID-Q2 resolution b, below):

| Phase entered | Signal origin (in `OmidCompatBridge`) → `transitionTo` site (in `sharc-container.js`) | Trigger | Exit |
|---------------|-----------------------------------|---------|------|
| `omid-active` | Signal emitted immediately after `AdSession.start()` resolves successfully (the existing `_createSession()` success path); container maps the signal to `transitionTo('omid-active')` in `sharc-container.js` | Publisher-page OMID session has started. This is router § 4.1's documented `omid-active` entry condition ("`AdSession.start()` returned successfully"). | → `omid-finishing` on `finish()`, or `terminated` on container teardown |
| `omid-finishing` | At the top of the `AdSession.finish()` path, before `_resetSessionRefs(true)` | Session is winding down; covers the `sessionFinish` grace window during which `sessionFinish` may still need to deliver to observers. The OMID spec specifies this window as "on the order of seconds, exact value left to the player" (Session Cleanup p.12) — **SHARC's chosen value is ~1.5s** (a SHARC implementation choice, not an OMID spec figure) | → `terminated` (container `_terminate()` already calls `transitionTo('terminated')` per router § 4.2) |

> **Interaction with `creative-active` (phase shadowing — I3).** The router's `creative-active` phase (router § 4.1) is the container's steady state and is entered by the container itself, independent of OMID. OMID's `omid-active` is a *narrower* window that opens *after* `AdSession.start()`, which itself happens after the container is live. So the real-world phase sequence is: `attaching-renderer` → `rendered` → `creative-active` → (`AdSession.start()`) → `omid-active` → (`finish()`) → `omid-finishing` → `terminated`. **Design note:** the router models phases as an open string set with one "current" phase (router § 4.3). Once `transitionTo('omid-active')` fires, it **permanently shadows `creative-active`** for the remainder of the container's life — the router has exactly one current phase and does **not** oscillate back to `creative-active` after the OMID session starts. This is **safe** because no live SHARC protocol declares any `creative-active`-only message type that must remain valid after the renderer is done: the renderer protocol's types are confined to `attaching-renderer`/`rendered` and are already out-of-phase by `creative-active`. So shadowing `creative-active` with `omid-active` strands no in-flight protocol surface. This is also why both `Register` (the shim defers it to `sessionStart`) and `Event` are gated to `omid-active` (+ `omid-finishing` for `Event`): the entire OMID surface lives in the post-`start()` window, and nothing OMID needs is valid in the pre-`omid-active` span. See OMID-Q1.

> **Resolved — OMID-Q2 (does OMID own `transitionTo`?): resolution (b), and it is REQUIRED, not merely preferred.** Router § 7.4 / RTR-D14: `transitionTo()` is called only from **container-internal** code paths and is **not** exposed to extensions. `OmidCompatBridge` is an extension and needs to reach `omid-active` / `omid-finishing`. Two candidate resolutions existed: (a) the container exposes a narrow, OMID-reserved `transitionTo` affordance to the OMID extension; or (b) the container itself drives the `omid-active` / `omid-finishing` transitions by observing the OMID extension's session lifecycle. **Resolution (b) is the only viable one — (a) is foreclosed, not just dispreferred.** Router § 9.6 **test #1** requires that *every phase string declared by any registered protocol's `types` map appears in some `transitionTo(...)` call site inside `src/sharc-container.js`*. If the OMID extension called `transitionTo` itself (resolution a), the `omid-active` / `omid-finishing` transition sites would live in `src/sharc-omid-bridge.js`, not `sharc-container.js`, and test #1 would fail. So the transition must be driven from the container. The OMID extension emits a container-internal lifecycle signal (the existing extension→container channel); the container maps that signal to `transitionTo('omid-active')` / `transitionTo('omid-finishing')` from within `sharc-container.js`, satisfying test #1 and preserving RTR-D14 / the router § 7.5 "phases are container-controlled" trust anchor.
>
> **Trust constraint (load-bearing).** The signal the container acts on MUST be sourced from the **publisher-page** OMID session lifecycle — specifically, `AdSession.start()` returning successfully on the publisher page (for `omid-active`) and the `finish()` path (for `omid-finishing`). It MUST **NEVER** be triggered by an inbound `SHARC:Omid:` envelope. An iframe-originated envelope can request nothing about phase: phases are derived only from publisher-page session state the creative cannot reach. See § 7.5 hardening checklist.

### 3.5 Envelope shapes (router-conformant)

Inbound (iframe shim → publisher), validated by the router gate:

```javascript

  sharcNonce: '<OMID protocolNonce — router gate step 7 validates>',
```

Outbound (publisher → iframe shim), built by `buildOutbound`:

Acceptable residue — the alternative (shipping a router instance into the hostile iframe) is strictly worse.

## 4. Exposure Timing & shim install

### 4.1 Install `window.omid3p` before `document.write(creativeHtml)`

Issue #217: "working assumption for `omid3p` exposure timing parallels existing MRAID / SafeFrame / SHARC bridge attachment." The renderer (Creative Markup variant) loads compatibility bridge modules from `data.bridges` **before** `document.write(creativeHtml)` — the same install point as `window.mraid` and `window.$sf.ext`. The 0.7.8 OMID shim installs at this point so the verification script's first synchronous read of `window.omid3p` succeeds (OMID `isSupported()` contract — § 9 dep 1).

### 4.2 `'omid'` stays out of `KNOWN_BRIDGE_IDENTIFIERS`

The 0.7.3 rationale stands — OMID is not an API-translation bridge; `KNOWN_BRIDGE_IDENTIFIERS` is reserved for creative-facing compat shims (MRAID, SafeFrame). Instead the renderer loads `sharc-omid-shim.js` as a separate, OMID-specific install:

- **Creative Markup variant (renderer):** the renderer accepts an `omid` boolean on the `SHARC:Renderer:render` envelope (which now flows through the router's `buildOutbound('SHARC:Renderer:', 'render', {...})` post-0.7.7-retrofit). When set, the renderer loads `sharc-omid-shim.js` from its same-origin allowlist (same security model as `loadBridgeModule`) **before** `document.write(creativeHtml)`.
- **Creative URL variant (`useMarkupInjection`):** `OmidCompatBridge.injectIntoMarkup(html)` — currently a no-op — prepends `<script src="<sharc base>/sharc-omid-shim.js"></script>` before any creative content, only when `omid3p` exposure is enabled (§ 12.3).
- **Creative URL variant (direct `iframe.src`, no markup access):** **not supported.** SHARC cannot inject a script into a frame whose markup it does not own; the container does not advertise `com.iabtechlab.sharc.omid`. Operator opt-in lever: `useMarkupInjection: true`. (Decision OMID-D11, carried.)

### 4.3 Trusted nonce injection into the shim (router § 16 dep 2)

The OMID `protocolNonce` (router-derived, delivered to the publisher-page extension via `onReady`) must reach the iframe shim **without** being creative-readable — **never** via `location.hash`, query string, or DOM attribute. Two viable mechanisms (router § 16 dep 2 leaves the choice to this design):

| Mechanism | How | Tradeoff |
|-----------|-----|----------|
| **(i) Renderer source-rewrite** | The renderer rewrites `sharc-omid-shim.js`'s source with the OMID `protocolNonce` baked into a closure constant *before* `document.write`, the same way the renderer pre-rewrites other injected modules. | Matches the renderer's existing module-injection path. Nonce never transits a creative-readable surface. Requires the renderer to know the OMID nonce at render time. |
| **(ii) `MessageChannel`-transferred at iframe creation** | At iframe creation the publisher posts the OMID `protocolNonce` over a one-time `MessageChannel` port (transferred, not broadcast). The shim's port-receive handler stashes it on private closure state. | Router § 16 dep 2's named alternative. The `MessageChannel` does **not** interact with the router (router owns `window.message`, not ports — RTR-D8). Slightly more iframe-side code. |

**Decision OMID-D2 (resolved — both variants specified, OMID-Q4 closed):**

- **Creative Markup (renderer) variant → mechanism (i), renderer source-rewrite.** The renderer rewrites `sharc-omid-shim.js`'s source with the OMID `protocolNonce` baked in as a **closure constant** before `document.write`, reusing the renderer's existing pre-rewrite path. The nonce never transits a post-load message or any creative-readable surface.

- **Creative URL + `useMarkupInjection` (`srcdoc`) variant → mechanism (ii), MessageChannel.** ⚠️ **PARKED — see issue #259.** This mechanism is non-functional in a real browser as specified: the `srcdoc` frame's sandbox omits `allow-same-origin` (SEC-001) → opaque origin → the steady-state `window.postMessage` event relay with a concrete `targetOrigin` (C1 forbids `'*'`) is silently dropped. The consumer set (opt-in × same-origin × wants-OMID × no-Option-2) is structurally near-empty; production OMID flows through the Markup variant (i). The text below is retained for the revival record; the small in-architecture fix is to relay OMID events over the transferred port (origin-agnostic), not `window.postMessage`. There is no renderer in this path, so source-rewrite (i) does not apply (OMID-Q4's old open edge). The mechanism is specified now:
  1. At iframe creation, the container constructs a `MessageChannel` and writes the shim into the `srcdoc` document so that the **shim prelude runs synchronously at the very top of the `srcdoc` document**, before any creative markup is written or parsed. (The shim `<script>` is the first child of `<head>`; `srcdoc` documents parse top-to-bottom, so the prelude executes before any later creative `<script>` or inline handler.)
  2. The container `postMessage`s one `MessageChannel` **port** into the `srcdoc` frame (transferred, not broadcast), with the OMID `protocolNonce` as the message payload, immediately after the frame is created.
  3. The shim prelude installs its port-receive handler **synchronously, as its first action**, and stashes the nonce as a **private closure constant** the moment the port message arrives. Because the prelude registered its `onmessage` before yielding to the event loop, and the creative markup has not yet executed any of its own code, the port message is delivered to the shim's handler first (though not exclusively — see correction below).

  **Ordering guarantee that makes "port consumed before creative runs" winnable.** The `srcdoc` document is parsed top-down. The shim prelude is the first script in the document and runs **synchronously during parse**, before the parser reaches any creative markup. It registers the port handler before the parse continues, so the shim is first to receive the nonce. The nonce is a closure constant by the time the first line of creative code executes.

  **Correction (the original claim here was wrong).** A transferred `MessagePort`'s *channel* is point-to-point once wired, but the port-*transfer message* is an ordinary `window` message: it reaches **every** `window.addEventListener('message')` listener in the frame, with the port readable as `event.ports[0]`. A creative inline script that registers a `message` listener before the transfer task dispatches **can** observe the transferred port — and therefore the OMID nonce. This does **not** breach the trust model, and the basis is **per-protocol nonce isolation, not port secrecy**: the OMID nonce is a distinct per-protocol HMAC derivation (router § 5.2, non-invertible — § 7.1 B1), so observing it yields **neither** the renderer-protocol nonce **nor** the root nonce, and the renderer nonce never enters this iframe (§ 4.3 closing paragraph below). With the OMID nonce a creative can forge only inbound `SHARC:Omid:Register` envelopes — gated to the **`omid-active`** phase (the only inbound-forgeable type; `Event` is outbound-only, so measurement events cannot be injected), rate-capped per § 7.3, and unable to drive phase. So only the renderer/root-nonce protection is load-bearing **for the trust-model boundary**; the OMID nonce authenticates only that no-privilege, phase-gated, capped inbound subscription surface. Deferring `SHARC:Omid:Unregister` (OMID-Q7, #263) removes the only inbound *mutation* a forged envelope could effect: there is no longer any inbound type that can tear down a co-tenant vendor's subscription, so the prior measurement-DoS residual (forging an `Unregister` against a co-tenant's shim-minted GUID) is eliminated entirely — a forged `Register` only adds a subscription scoped to the forging creative's own iframe shim. This parallels OMID-D5's accepted principle that hostile creative code observing the relay is in-scope, and the same conflation #254 corrects for the Markup path (closure/source unreachability ≠ message-transfer unreachability). This is the same "secret consumed before hostile code runs" property the renderer source-rewrite gives the Markup variant, achieved without a renderer.

The OMID `protocolNonce` is never placed on `location.hash`, query string, or any DOM attribute in either variant.

The OMID `protocolNonce` and the renderer-protocol nonce are **different** per-protocol nonces (router § 5.2: each prefix derives independently). Leaking the OMID nonce does not let the creative forge renderer envelopes (router § 7.1, layer 1). Leaking the renderer nonce — which never enters the iframe — is structurally prevented.

## 5. `omid3p` Surface Contract (IAB-spec core)

This is the whole point of 0.7.8 and is **not** weakened by the router consumption. Verified against IAB `Open-Measurement-JSClients` at `src/verification-client/verification-client.js`.

### 5.1 Public API (the contract verification scripts depend on)

`getThirdPartyOmid()` accepts an object iff it exposes both methods as functions:

```javascript
window.omid3p = {
  /**
   * Register a session-wide observer that receives ALL session events.
   * @param {function(event)} observer - receives { adSessionId, timestamp, type, data }
   * @param {string=} vendorKey - optional vendor identifier
   * @param {string} injectionId - opaque id supplied by the verification client
   */
  registerSessionObserver: function (observer, vendorKey, injectionId) { ... },

  /**
   * Register a single-event-type listener.
   * @param {string} eventType - one of the IAB OMID event-type strings (§ 5.3)
   * @param {function(event)} listener - receives { adSessionId, timestamp, type, data }
   * @param {string} injectionId - opaque id supplied by the verification client
   */
  addEventListener: function (eventType, listener, injectionId) { ... }
};
```

**Nothing else is on the contract.** SHARC must not expose additional methods on `window.omid3p`. Verification scripts probe `omid3p && typeof omid3p['registerSessionObserver'] === 'function' && typeof omid3p['addEventListener'] === 'function'` (the OMID `isSupported()` contract — § 9 dep 1). Adding surface invites coupling to SHARC-specific APIs that will not survive OMID spec revisions. **Critically: the OMID `protocolNonce` is NOT on this surface and never reaches any observer callback, return value, or payload (§ 9 dep 6).**

> **Note (`injectionId` is not a guaranteed spec parameter).** The OMID spec interface signatures are **two-param**: `registerSessionObserver(observer, vendorKey)` and `addEventListener(type, listener)`. The IAB reference Verification Client (omsdk) passes the third `injectionId` argument to **`registerSessionObserver`** (i.e. `registerSessionObserver(observer, vendorKey, injectionId)`), while **`addEventListener`** is called with only `(eventType, listener)` — no `injectionId`. SHARC's shim **defensively accepts an extra arg** on both methods (harmless, and it matches the reference client's actual call shapes), but implementers should not treat `injectionId` as a spec-guaranteed parameter — it is a reference-client convention, not part of the documented signatures.

### 5.2 Event shape delivered to observers

```javascript
{
  adSessionId: '<OM SDK session id from publisher-page AdSession>',
  timestamp:   <ms since epoch — publisher-side wall clock>,
  type:        '<string, see § 5.3>',
  data:        { /* event-type-specific payload, may be empty {} */ }
}
```

`adSessionId` is the OM SDK Session Client's session id read off the publisher-page `AdSession` after `start()`; reused for every event in the session, matching the OMID spec. **The envelope's `sharcNonce` / `placementSessionId` / `sequence` transport fields are stripped by the shim — they never appear in the observer event** (§ 9 dep 6).

> **Develop-phase flag — `sessionStart` `data` carries a structured `context`.** The generic `data: {}` placeholder above is under-specified for `sessionStart`. The OMID spec's `sessionStart` `data` carries a structured `context` object (`apiVersion`, `environment`, `accessMode`, `adSessionType: 'html'`, `omidJsInfo`, and related fields — Implementation Guide p.13–15). The develop phase MUST enumerate those fields for the `sessionStart` event rather than emitting a bare `data`. Flagged here, not fully spec'd — the exact field set is finalized when the shim is wired to the real Session Client surface.

### 5.3 Event types supported in 0.7.8

Subset matching what `OmidCompatBridge` already fires on the publisher-page `AdSession`:

| EventType | When fired | Source on publisher page |
|-----------|-----------|--------------------------|
| `sessionStart` | After `AdSession.start()` succeeds | `registerSessionObserver` callback `type==='sessionStart'` |
| `sessionFinish` | After `AdSession.finish()` | `registerSessionObserver` callback `type==='sessionFinish'` |
| `sessionError` | OM SDK reports a session error | `registerSessionObserver` callback `type==='sessionError'` |
| `loaded` | After `AdEvents.loaded(...)` | Synthesized by bridge at `_fireLoaded()` |
| `impression` | After `AdEvents.impressionOccurred()` | Synthesized by bridge at `_fireImpression()` |
| `geometryChange` | On viewability/placement change | Synthesized at `_signalVisibility` / `_handlePlacementChange` |

**Deferred to follow-up issues:** video-specific event types (`start`, `firstQuartile`, `midpoint`, `thirdQuartile`, `complete`, `pause`, `resume`, `bufferStart`, `bufferFinish`, `skipped`, `volumeChange`, `playerStateChange`, `adUserInteraction`). 0.7.3 § 8.1 already lists these as future work; the shim mirrors that coverage.

`addEventListener` accepts any event-type string; if the shim hasn't been wired to fire that type, the listener is registered and silently receives nothing. **No `OMID_UNSUPPORTED_EVENT_TYPE` error** — verification scripts probe broadly and rely on absence-of-event semantics.

### 5.4 Observer invocation rules

- `registerSessionObserver` observers receive every event in the active session, in delivery order (matches the IAB OMID spec).
- `addEventListener(eventType, ...)` listeners receive only matching-`type` events.
- A verification script that registers **after** events have already fired gets **full replay**: the shim caches every previously-fired event and, on subscription, synchronously invokes the new observer/listener with **each previously-fired event of the subscribed type, in chronological order**, before delivering live events. A `registerSessionObserver` observer is replayed the entire session event log to date; an `addEventListener(type)` listener is replayed every prior event of that `type`. (`addEventListener` for a type the shim hasn't been wired to fire replays nothing, because nothing was cached.)
- `loaded` / `impression` are session-singletons (already guarded by `OmidCompatBridge._fireLoaded`/`_fireImpression`), so each appears at most once in the replay log.

> **Replay is sacred — the spec-faithful invariant.** The replay path is **full, literal, chronological, and per-type. No replay-time cap, no replay-time coalescing, no replay-time sampling — ever.** When an observer/listener subscribes, every previously-fired event of the subscribed type is delivered in the order it fired. Bounding the replay (e.g. coalescing `geometryChange` at replay time, or replaying only the most-recent `sessionStart`) would **skip already-fired events** and violate OMID Event Caching (Implementation Guide v1.0 p.13). This is the same category of error as the cap-1 narrowing already reversed (OMID-Q5). **All amplification bounding happens at the two inputs to replay (§ 7.3) — never on the replay path.**

> **Resolved — OMID-Q5 (replay/catch-up is spec-baseline behavior, NOT beyond spec).** Late-registrant catch-up is **mandated** by the OMID spec, not a SHARC judgment call. OMID Web Implementation Guide v1.0, "Event Caching" (p.13): *"Upon subscription to an event, the player should invoke the given handler with each previously fired event of that type in chronological order."* The Ad Session Lifecycle (step 8) reinforces this: a verification script that registers after events have fired must be brought current. These are spec `should`s — baseline behavior, not beyond-spec. SHARC implements them **faithfully via full replay** (all previously-fired events of the subscribed type, in order — the bullet above). The prior draft's narrowing to a single most-recent `sessionStart` (cap 1) and its "beyond the OMID spec's letter" framing were **incorrect** and are reversed.
>
> The spec's sanctioned **alternative** — deferring ad playback until all verification vendors have registered, so no catch-up is needed — was considered and **not taken**: SHARC cannot block the publisher's ad render on vendor-script registration timing, and the inline-`adm` delivery model (vendor scripts arrive with the creative, not before it) makes "wait for all vendors" undefined in practice. Full replay is the correct faithful implementation for SHARC's delivery model.
>
> **Amplification is bounded at the two inputs to replay, never at the replay.** Replay cost is `O(observers × cached_events)`. Because replay itself is full and literal (no cap, no coalescing), both factors are bounded at their *inputs*: the **observer count** by the cumulative-register-calls/session subscription cap, and the **cached-log size** at *emission* (fewer events are ever fired, so full replay of the fired set stays spec-faithful). Neither bound touches the replay path. See § 7.3.

### 5.5 Out-of-session calls

If a verification script calls `registerSessionObserver` / `addEventListener` before `OmidCompatBridge` has created its `AdSession` (publisher-page OM SDK still loading), the shim **queues the subscription locally and does NOT post `SHARC:Omid:Register` yet**. It materializes the subscription — and posts the deferred `Register` envelope(s) to the publisher — **at `sessionStart`**, once the OMID session exists (and therefore once the OMID `protocolNonce` has resolved on the shim side, § 3.2). There is **no ack-correlation**: the OMID surface is observer-only (register → events flow → session ends), with no registration acknowledgment in the contract and no vendor unregister method anywhere, so the publisher never sends a response the shim must correlate (OMID-Q7, deferred — #263). The `subscriptionId` each `registerSessionObserver` / `addEventListener` mints is a **shim-side dispatch key** for the live `subscriptions` registry (it keys local fan-out, § 7.2) — not an `Unregister` scope and not a `callbackMap` correlation token.

> **OMID-Q1 cross-ref (resolved):** because the shim defers posting `Register` to `sessionStart`, the `Register` phase membership in § 3.2 is `omid-active` only. Queue-vs-post timing and the phase gate are locked together (§ 3.2).

```mermaid
    Iframe->>Pub: postMessage SHARC:Omid:Register<br/>(signed w/ OMID nonce; router gate validates)

    Note over Pub: AdSession.start() succeeds
    Pub->>Pub: protocolRouter.transitionTo('omid-active')
    OMSDK-->>Pub: sessionStart (via registerSessionObserver)
    Pub->>Iframe: buildOutbound('SHARC:Omid:','Event',{type:'sessionStart'})
    Iframe->>Vscript: cb({adSessionId, type:'sessionStart', ...})

    Pub->>OMSDK: AdEvents.loaded(...)
    Pub->>Iframe: SHARC:Omid:Event {type:'loaded'}
    Iframe->>Vscript: cb({type:'loaded', ...})
    Pub->>OMSDK: AdEvents.impressionOccurred()
    Pub->>Iframe: SHARC:Omid:Event {type:'impression'}
    Iframe->>Vscript: cb({type:'impression', ...})

    Note over Pub: container teardown
    Pub->>Pub: protocolRouter.transitionTo('omid-finishing')
    Pub->>OMSDK: AdSession.finish()
    OMSDK-->>Pub: sessionFinish
    Pub->>Iframe: SHARC:Omid:Event {type:'sessionFinish'}
    Iframe->>Vscript: cb({type:'sessionFinish', ...})
    Iframe->>Iframe: drop window.omid3p (refuse new subscriptions)
    Note over Pub: _terminate() → transitionTo('terminated')
```

### 6.2 Where the publisher-page bridge taps into OM SDK

`OmidCompatBridge._createSession()` already calls `self._omid.adSession.registerSessionObserver(...)` (`src/sharc-omid-bridge.js` L865–871). 0.7.8 extends that observer to:

1. On every event from OM SDK, build the envelope via `buildOutbound('SHARC:Omid:', 'Event', {...})` and post it to the iframe's `contentWindow`.
2. Track the iframe origin captured at iframe creation (same value as `this._rendererOrigin` for the Markup variant; for the URL `srcdoc` variant the origin may be `null`/opaque — § 7.4).
3. Emit a publisher-page session-lifecycle signal on `start()` success and on `finish()`; the container maps these to `transitionTo('omid-active')` / `transitionTo('omid-finishing')` from within `sharc-container.js` (OMID-Q2 resolution b — the `transitionTo` site is container-internal, never extension-exposed, and never triggered by an inbound envelope).
4. Continue the existing `sessionFinish` → `_resetSessionRefs(true)` cleanup plus a final teardown envelope.

For `loaded` / `impression` / `geometryChange` (synthesized by the bridge, not emitted by OM SDK), the bridge posts the envelope at the same call sites where it currently calls `_fireLoaded` / `_fireImpression` / `_signalVisibility`.

### 6.3 Events flow one way

The IAB `omid3p` surface is **observer-only**. Verification scripts subscribe; they do not emit. There is no `omid3p.publishEvent()` — vendor measurement signals flow vendor-script → vendor-CDN over the script's own HTTP fetch, not back through `omid3p`. So the OMID router protocol is **unidirectional** for events (`Event` is `outbound` only) and the only inbound type is the observer registration (`Register` is `inbound`). There is no inbound unregister — the `omid3p` surface has no removal method, so registrations are never torn down individually (OMID-Q7, deferred — #263). The `types` map in § 3.2 encodes exactly this asymmetry.

### 7.1 Inherited from the router (do not re-derive here)

The **only** new-to-OMID gate the router does *not* provide is the **shim-side inbound validator** (§ 3.5 / OMID-Q3) — because the router is a publisher-page primitive and there is no router instance inside the hostile iframe. That validator is 4 checks, pinned by test (§ 10).

### 7.2 OMID-specific residue: cross-vendor isolation (router § 16 dep 5)

The router correctly draws the boundary at "one protocol = one nonce + one handler" (router § 16 dep 5). **Cross-vendor isolation inside the creative iframe is 0.7.8's responsibility** — the router cannot help, because it never sees inside the iframe.

The threat: multiple vendor verification scripts run in the same creative-iframe JS context. The shim must dispatch each session event to each registered observer **without** letting a hostile vendor script harvest another vendor's events.

- **Canonical (OMID same-window dispatch):** the shim invokes each registered observer's callback **directly** in the same JS context (`observer(event)`), exactly as OM SDK's own same-window model does. This is **not** a cross-frame call and **not** a broadcast.
- **Forbidden:** `iframe.contentWindow.postMessage(...)` for shim→vendor delivery. A broadcast `postMessage` is visible to *every* `message` listener in the iframe — including a hostile vendor script that subscribed to harvest competitors' events. The shim must use direct callback invocation, never in-iframe broadcast.
- **Per-vendor `MessageChannel` (edge case):** if a vendor's verification script ever lives in its *own* nested iframe (uncommon for OMID v1.5 in-shim integration), a dedicated port per vendor avoids the broadcast leak. Out of scope for the common case; noted for completeness.

> **Decision OMID-D5 (locked, carried):** the shim is a **faithful relay**, not an information channel. The `data` payload mirrors exactly what OM SDK delivers to a same-frame OMID integration — no SHARC-specific or publisher-page-specific fields. Hostile creative code observing events is an accepted OMID-spec threat (the creative author chose which verification scripts to inline). What SHARC must not do is *add* sensitive data to the relay.

### 7.3 OMID-specific residue: amplification bounded at the inputs, never at the replay

Replay (§ 5.4) is full and literal — `O(observers × cached_events)` per session, where `cached_events` grows with session duration. The spec-faithful resolution is that **the replay path is never bounded**; instead **amplification is bounded at the two inputs to replay, neither of which is the replay itself.** A hostile creative would otherwise register thousands of observers (each forcing a full replay of the cached log) and/or drive a high-frequency event (`geometryChange` on resize churn) to grow the cached log, for `O(observers × events)` amplification. Both arms are cut at the input.

**Input 1 — observer count → the cumulative-register-calls/session cap.** The enforced unit is the **total number of `register` calls (`registerSessionObserver` + `addEventListener`) over the session's lifetime**. `window.omid3p` exposes **no** vendor unregister / `removeEventListener` surface, so a subscription is never removed: the live subscription count never decreases and is always equal to the cumulative register-call count. A single cumulative ceiling is therefore the honest, sufficient bound on the observer factor — each `register` increments the count, and the count never resets. Calls past the cap are accepted silently and ignored (same surface as a vendor SDK that ignores registration internally — no error, no throw).

There is **no `register → unregister → register` churn to defend against**: with no unregister surface, that loop is unreachable. (A live-count cap and a cumulative cap would coincide exactly here, so the earlier two-arm framing was redundant.) If a future OMID spec revision introduces a vendor unregister / `removeEventListener` surface, revisit a true concurrent-live cap — option (b), deferred (ref #252).

**Input 2 — cached-log size → bounded at EMISSION, not at replay.** The key principle: **emission cadence is the player's prerogative — the OMID spec does not mandate a `geometryChange` rate** — so rate-limiting or sampling *at emission* means fewer events are ever **fired**, and full replay of the fired set remains spec-faithful. This is **categorically different** from coalescing at replay time (which would skip already-fired events and violate Event Caching). Emission-side bounds:

- **`geometryChange`:** the publisher-page bridge rate-limits emission to **≤1 event / 100ms** (matches OM SDK Service Script's internal throttle). Frame this as a **sampling cadence — the player's choice**, not a replay alteration: a sampled event is simply never fired, so it never enters the cached log and never needs replay. A **coarser cadence is a tunable** if #244's session-profile data shows that session-duration replay cost is pathological. Emission-side, spec-clean.
- **`sessionError`:** an **emission-side cap on the number of distinct cached `sessionError`s**, so an OM-SDK error-storm cannot grow the cache unboundedly. Errors past the cap are not cached (and so not replayed). Emission-side, spec-clean.
- **Session-singletons** (`sessionStart` / `sessionFinish` / `loaded` / `impression`) are already ≤1 each (guarded at the bridge), so they contribute a constant to the cached log.

**The subscription cap is NOT "the single load-bearing guard."** It bounds only the observer factor. Amplification is bounded at **both** inputs — the observer cap **and** the emission-side event-rate bounds — while the replay itself stays full per spec.

**Accepted residue (documented honestly).** Per-session replay cost still grows with session duration: a long session accumulates a longer (sampled) cached log, and each late registrant replays all of it. This is the **deliberate, accepted price of spec-faithful full replay** — bounding the replay path would violate Event Caching. The input bounds (observer cap + emission rate-limits) keep the cost tolerable. **#244's corpus data** (session profiles + observer-count distribution) confirms whether per-session replay cost is ever pathological in practice and informs both the emission cadence and the cap value. Revisit only if the data warrants.

> **Decision OMID-D6 (mechanism locked; observer-cap VALUE provisional, owned by #244).** The amplification model — **bound the two inputs to replay (observer count + emission-side event rate), never the replay path** — is locked (this revision). The subscription-cap **mechanism** is a single honest unit: **cumulative register-calls per session** (there is no vendor unregister surface, so live count never decreases and equals the cumulative count — a separate concurrent-live arm would be redundant). The emission-side bounds (`geometryChange` ≤1/100ms sampling cadence, distinct-`sessionError` cap) are locked. The subscription-cap **VALUE is provisional pending #244 corpus measurement**: #244's validator measures the **cumulative-register-calls/session distribution** (median / p99 / max) across the real DV/IAS/Moat/Integral vendor scripts against the corpus and sets the cap at **p99 + headroom** on that unit. `MAX_OMID_SUBSCRIPTIONS` ships as a tunable constructor option whose **provisional default MUST be a finite, conservative value** — the cap is enforced from day one; #244 only tunes the number. **Do not let "value TBD pending #244" read as ship-unbounded, and do not bake 64 as final.** The subscription cap is not the single guard — it bounds the observer factor only; emission-side bounds cut the cached-log factor. If a future OMID spec revision adds a vendor unregister / `removeEventListener` surface, revisit a true concurrent-live cap (option (b), deferred — ref #252).

### 7.4 OMID-specific residue: srcdoc / opaque-origin shim-side validation

For the Creative URL + `useMarkupInjection` variant, the iframe is `srcdoc`. Chromium srcdoc iframes inherit the parent origin; Safari and others may give `null` / opaque origin. The **shim-side** inbound validator (§ 3.5) cannot rely on `event.origin` alone.

**Mitigation:** the shim's inbound check treats `event.source === window.parent` as load-bearing and `event.origin` as best-effort: pass if origin is non-null and matches the recorded origin; pass if origin is `null`/opaque and `event.source === window.parent`; fail otherwise. The injected OMID `protocolNonce` is the second-layer defense. On the **publisher side**, the router gate's step 2 (`event.source === iframe.contentWindow`) is unaffected by opaque origin — `contentWindow` identity is browser-set and unforgeable (router § 7.5). The opaque-origin concern is therefore confined to the shim's own validator.

> **Decision OMID-D9 (architectural judgment, security implications):** best-effort origin + load-bearing `event.source` for the shim-side validator. **Needs Security Engineer review pass.** Note this is *narrower* than the parked draft framed it: the publisher-side gate is the router's and is opaque-origin-safe via `contentWindow` identity; only the shim's own inbound validator deals with opaque origin.

### 7.5 Hardening checklist (Code Reviewer + Security Engineer pass)

- [ ] OMID registers `prefix: 'SHARC:Omid:'` with correct `types`/`phases`/`direction`; no bespoke `window.addEventListener('message', ...)` in the OMID extension.
- [ ] Outbound envelopes built via `buildOutbound`; no hand-stamped `sharcNonce`/`placementSessionId` on the publisher side.
- [ ] OMID `protocolNonce` never appears in any observer callback, return value, or `data` payload (§ 9 dep 6 — pin a test).
- [ ] Shim-side inbound validator: 4 checks (source/origin/nonce/placementSessionId); rejects each failure (§ 3.5 / OMID-Q3 test).
- [ ] Cross-vendor delivery is direct callback invocation, never in-iframe `postMessage` broadcast (§ 7.2).
- [ ] Subscription cap enforced on the shim side on a single honest unit: **cumulative register-calls per session** (no vendor unregister surface exists, so live count equals the cumulative count — § 7.3). Cap value is provisional pending #244, but the provisional default is **finite and conservative** — never ships unbounded.
- [ ] **Replay path is never capped, coalesced, or sampled** (§ 5.4 invariant): a late registrant receives every previously-fired event of the subscribed type, in order. Bounding happens at the inputs, never the replay (§ 7.3).
- [ ] Emission-side cached-log bounds in place: `geometryChange` rate-limited to ≤1/100ms (sampling cadence); distinct cached `sessionError`s capped so an error-storm cannot grow the cache unboundedly (§ 7.3).
- [ ] Phase transitions (`omid-active` / `omid-finishing`) driven only via the OMID-Q2-resolved path (container-internal `transitionTo` in `sharc-container.js`, not extension-exposed). **The transition trigger MUST be sourced from publisher-page OMID session state (`AdSession.start()` success / `finish()`) and MUST NOT be derived from any iframe-originated `SHARC:Omid:` envelope** (§ 3.4 trust constraint).
- [ ] Logging discipline: no envelope payload contents in logs (counts + rejection reasons only).

### 13.1 Does the locked #217 decision need revisiting?

**No.** The #217 lock (omid3p primary path; `verificationScripts` supplementary; consume the router) holds cleanly under the router. One nuance, now **resolved**: #217's acceptance criterion says events "propagate via a SHARC Protocol Router protocol (prefix `SHARC:Omid:`), with envelope types and lifecycle phases declared" — this design satisfies that literally (§ 3.2, § 3.4). OMID-Q2 surfaced a tension between "OMID drives phase transitions" and the router's RTR-D14 ("phases are container-controlled, `transitionTo` not extension-exposed"); it is resolved in favor of **container-driven transitions off a publisher-page OMID signal**, which router § 9.6 test #1 in fact *requires* (the `transitionTo` site must live in `sharc-container.js`).
