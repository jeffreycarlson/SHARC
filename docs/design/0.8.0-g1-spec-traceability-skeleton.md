# ADR: G1 Spec Traceability Skeleton (0.8.0)

## Context

G1 of the 1.0 Definition of Done requires the spec reorganized into the ratified three layers (Runtime / Creative API / Compat Profile), such that an implementer can determine from the docs alone which conformance class any requirement belongs to. Discovery is closed; all rulings ratified 2026-07-08: extraction-not-rewrite; three normative documents under the umbrella **"SHARC Specification 1.0 (Draft)"** with independent spec versioning; N/I/H banner on every docs/ file; a conformance clause defining "SHARC Core conforming" (= L1+L2; Compat Profile is an OPTIONAL add-on); MUST-to-gate traceability (which becomes G4's checklist); consolidated security model; wire-format/SDK separation; citable registries; SHARC-legacy WG drafts harvested and formally superseded; docs site out; third-party IAB library stays private.

The estate survey (this pass) found:
- **The normative text is scattered and mostly not RFC-2119.** 232 uppercase RFC-2119 keyword occurrences across 23 files (167 lines) — but the wire spec of record, `docs/api-reference.md` (1,818 ln), contains only **3** RFC-2119 lines (plus ~15 lowercase "must" sentences). Its normative content is declarative prose ("The container validates…"). The heaviest RFC-2119 densities sit in `docs/design/state-delivery-contract.md` (34 lines), the point-in-time 0.7.x design docs (25/22/12/10), and `docs/proposals/creative-sources.md` (13) — i.e. in design records, not the citation-facing docs. Consequence: the traceability table must be built at the **clause** level during extraction; a keyword grep alone under-counts the real normative surface by roughly an order of magnitude.
- **The mis-filed security spec is confirmed.** `docs/proposals/creative-sources.md` (1,304 ln) carries the RFC-2119 conventions block, the glossary, and the full threat-model section (§ Security Model: malicious renderer, untrusted markup, cross-impression amplification, wrapper-iframe topology, CSP layering, click-jacking, top-nav user-activation, Fenced Frames, SharedArrayBuffer) — the largest single block of L1 security prose, filed as a "proposal."
- **The wire/JS entanglement in api-reference.md is real but splits cleanly**: §§2–8 + §11 + both appendices are wire-format; §1 (constructor, stamping, isolation guard) and §§9–10 are container-behavior (L1) and SDK surface.
- **The root README embeds a normative OMID mini-spec** (lines ~125–241: operator integration, bid-signaled auto-install, "What's shipped" behavior guarantees, verification).
- **The corrected trust story is spread over three places**: protocol-router design §5.2/§7.1 (per-protocol HMAC nonce derivation), the 0.7.8 §4.3 correction (port-transfer observability; nonce isolation, not port secrecy), and creative-sources §Security Model.
- **Every corpus-proven behavior already has a named gate.** `test:all:built` enumerates ~85 suites; the validator carries the MRAID staged-gate ladder (#419) and the G5 U1–U3 URL ladder with ratified bucket vocabulary. The raw material for MUST→gate rows exists; nothing needs new test invention at skeleton time.

## Decision

Adopt the appendix below as the **extraction map**: three document outlines where every section row names its source (estate file § / SHARC-legacy § / NEW-PROSE) and its pinning gate (or NO-GATE), an N/I/H disposition for every docs/ markdown file plus the root README (72 files on this branch — the count grows as design docs land; the contract is the RULE, not the number), the citable-registry list, conformance-clause and versioning-policy bullet skeletons, and the NEW-PROSE inventory. Working rule holds: if a sentence exists and is corpus-proven, move and label it; write new prose only where the estate is silent (8 places, listed).

Structural decisions made here (within the ratified rulings, not reopening them):
1. **New specs live at `docs/spec/`**: `container-runtime.md` (L1), `creative-api.md` (L2), `compat-profile.md`, plus `registries.md` and `traceability.md`. `docs/spec/` becomes the only NORMATIVE-status directory once extraction lands; the five current normative-of-record files flip to HISTORICAL with supersession pointers in the same PR that moves their prose.
2. **Banner semantics** (machine-readable, one line, HTML comment so it renders invisibly): `<!-- SHARC-DOC-STATUS: NORMATIVE -->` — binds implementers; `INFORMATIVE` — guidance/rationale/research, never citable as requirement; `HISTORICAL` — point-in-time record, superseded or archival, never load-bearing. Exactly one banner per file, within the first 10 lines.
3. **Checker scope = every `docs/**/*.md` + root `README.md`.** The ruling says every docs/ file; `docs/design/` is explicitly IN (it holds three of the five normative-of-record files — excluding it would exempt exactly the files most likely to be mistaken for spec). Root README is in scope because it carries the OMID mini-spec until extraction. Non-markdown (`pages-landing.html`, `size-history/*.json`) out — banners are a prose contract.
4. **The SDK reference is an informative annex of L2**, not normative text: L2's normative content is the wire format (messages, ordering, state-delivery invariants), stated so a third party can implement a creative-side library without reading our JS. `sharc-creative.js` usage examples and the cookbook stay INFORMATIVE.
5. **HTML lifecycle adapter is L1, not Compat.** The plain-HTML floor is a runtime obligation (G5 ratified it as the first-class floor); the Compat Profile is only MRAID/SafeFrame bridge behavior.
6. **G6 seam reserved verbatim**: L1 carries "§ In-App Integration (WKWebView / Android WebView)" with subsection "OMID In-App", source `G6 design pass (in flight)`. Nothing else in this skeleton touches G6 material.
7. **Red structural check ships now** (`scripts/check-doc-banners.js`, `npm run test:spec-structure`, NOT in `test:all`): banner check is real and red against today's estate (zero banners exist); the MUST→traceability check is a designed placeholder that activates when `docs/spec/traceability.md` exists.

## Consequences

- The skeleton makes the extraction PR-able in slices: each L1/L2/Compat section row is a move-and-label unit with its gate named, so review = "does the moved prose still say what the gate pins?"
- The MUST census number (232) becomes an honesty floor, not the table's row count — the table will be clause-indexed and larger; G4's succession check consumes it.
- Banner-flipping the five normative-of-record files to HISTORICAL is deferred to the extraction PRs (flip-on-supersede, per ratify→propagate); until then they carry NORMATIVE banners and the checker holds the estate accountable either way.
- NO-GATE rows (14 across the three outlines) are concentrated where expected: scope/terminology/conformance boilerplate and the G6 reserved slot. Two are flagged as *gate-desired* follow-ups (extension framework negotiation; compat sunset posture has none by nature).
- What we give up: the point-in-time 0.7.x design docs stop being quotable as spec (HISTORICAL), which will occasionally force a registry or spec-section lookup where a design doc used to be the habit. That is the point.
- Follow-on work not in this skeleton: getting-started Level-0 lead rewrite (G1 bullet 3), Moat reference cleanup (G3 note), the actual traceability.md population, and activating checker phase (b).

## F. Conformance-clause skeleton (bullet outline, not prose)

- Conformance classes: **Container Runtime** (mandatory), **Creative (wire)** (optional class), **Compat Profile** (optional add-on). The reference SDK is not a conformance class.
- "**SHARC Core conforming**" ≝ satisfies L1 + L2. Compat Profile conformance is claimed separately ("SHARC Core + Compat Profile").
- RFC-2119 conventions block (moved from creative-sources.md §Conventions).
- Named acceptance suites: `npm run test:all` / `check:ci` (reference-implementation gate); creative-validator staged gate ladders — MRAID markup gates (#419) and URL gates U1–U3 with the ratified bucket vocabulary; corpus practice per DoD §G2 posture (ongoing vigilance, refresh cadence opportunistic).
- Authority ordering: **normative prose > reference implementation > test suite**; any divergence is a bug in the lower authority; filing path stated.
- Class-determination rule (the G1 check itself): every requirement carries its class in-section; the traceability table is the index.
- **Profile-governance rule (RATIFIED 2026-07-08, post-challenge):** *no optional class or add-on profile may ever be required to claim SHARC Core conformance.* Normative, permanent — the guard against optional-becomes-de-facto-mandatory (the `supports()` failure mode).
